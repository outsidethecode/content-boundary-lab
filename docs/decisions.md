## 1. What the project is

- A secure code review and remediation lab. The FastAPI/SQLite app is the system under review, and the default build is its remediated state.
- Every vulnerability is deliberately constructed ("seeded"), never "found". Fixed sentence (Addendum C1): *"Every vulnerability here is deliberately constructed for education; none is a discovery in any third-party system."*
- Three trust decisions structure the code, the findings and the README: identity, authorisation and content trust.
- Controls are always labelled as implemented, simulated or conceptual.

**AM-11: M1D decisions (2026-11-03).** Approved by the security reviewer. M1D is split into M1D-1 (clock), M1D-2 (store) and M1D-3 (audit).
- **Storage:** SQLite `STRICT` tables, so SQLite 3.37 or newer is required; schema compatibility is recorded with `PRAGMA user_version`. Timestamps are `INTEGER` microseconds since the Unix epoch, UTC.
- **Identifiers:** opaque server-generated UUIDs for productions, engagements and assets; integer ids for subjects.
- **Model:** coordinators and vendors share the `subjects` and `engagements` structures. For this MVP there is one engagement row per `(subject_id, production_id)`; renewal and historical re-engagement are out of scope. There is no `starts_at`. The 90-day cap (A10, a lab assumption) is enforced in M1F, not in the schema.
- **Revocation (M1D-2):** one-way, enforced by a trigger.
- **Audit (M1D-3):** actions are validated against an application-level closed vocabulary. Triggers reject `UPDATE`, `DELETE` and an overwriting insert (a `BEFORE INSERT` collision guard, because `INSERT OR REPLACE` bypasses delete triggers; verified on SQLite 3.50.4), and an authorizer on application connections denies changes to the audit objects. Schema initialisation uses a separate connection so these restrictions do not block schema creation. The table is not tamper-evident (M0).
- **Connections:** explicit transactions, and a connection per request once routes exist. `Dependencies` stays unchanged throughout M1D.
- **Clock (M1D-1):** `clock.py` provides the `Clock` protocol, `SystemClock` (UTC) and `to_micros`/`from_micros`, which use integer arithmetic only and reject naive datetimes. Tests use a manual clock. The check that only `clock.py` reads system time is deferred to M1F.
- **Store (M1D-2):** `store.py` holds one complete initial schema (version 1, no migrations): five `STRICT` tables, one index and eight triggers. `initialise_schema` is the only code that creates tables; it runs in one transaction, does nothing for version 1, and refuses a non-empty unversioned database or any other version. `connect` opens an existing database read-write only (it never creates one), rejects any other `user_version`, enables `foreign_keys` before any transaction and verifies it, and waits at most 5 seconds for a lock (a lab assumption). Writes use `transaction()`, which takes `BEGIN IMMEDIATE` and rolls back on any exception. Identifiers are 32-character lowercase hex, and `display_name` fields are metadata that is never used as a path.
- **Revocation is final (M1D-2):** once `revoked_at` is set, the whole engagement row is immutable. Triggers reject any update of it (even one that changes nothing) and any delete, and reject an `INSERT OR REPLACE` or `UPDATE OR REPLACE` that would overwrite it by colliding on its id, its rowid or its `(subject_id, production_id)` pair, so the pair stays taken. A subject's `(issuer, subject)` identity is fixed by a trigger, so a revoked identity cannot be freed by renaming its subject row; `display_name` is metadata and may change. Parent keys are held by the foreign keys. `store.py` makes no authorisation decision; the engagement lookup is M1F.
- **Audit table (M1D-2):** the table and its three triggers (update, delete, overwrite) are in the initial schema so there is a single schema version. They reject those SQL statements on any connection. They do not stop a privileged connection from dropping the triggers, or anyone from editing the file, and the table is not tamper-evident. The audit API and the application-connection authorizer remain M1D-3.

**AM-12: M1D-3a transactional audit API (2026-11-03).** Approved design for the audit API part of M1D-3, implemented in `audit.py`. M1D-3 is split into M1D-3a (this API) and M1D-3b (the application-connection authorizer and a schema fingerprint check at connect), which has not started.
- **Append:** `record_event(conn, clock, action, outcome, *, actor, ...)` requires a transaction that is already open on the caller's connection (the caller's `store.transaction()`). It runs one parameterised `INSERT` into `audit_events`, returns the generated sequence number, and never commits or rolls back. Outside a transaction it raises `StoreError` before writing anything. The timestamp comes from the injected clock through `to_micros`.
- **Atomicity:** a workflow that changes state calls `record_event` inside the same `store.transaction()` as the change, so the two commit together or not at all. If the audit insert fails, the error propagates and the change is rolled back; there is no best-effort logging after a failed insert. The API does not make any store mutation audited by itself: the duty to audit each mutation is established workflow by workflow from M1F. A denial that changes no state is recorded in its own short transaction.
- **Vocabulary:** the closed `StrEnum`s `AuditAction`, `AuditReason`, `ObjectType` and `Outcome` (the last matches the table's `CHECK`). Plain strings are rejected. Adding a member is a reviewed change; values are lowercase and at most 64 characters. `AuditReason` holds machine codes only, so request text is never stored as a reason. `NOT_FOUND_OR_FORBIDDEN` is one code, so the record does not distinguish an object that does not exist from one the caller may not see.
- **Actor:** `Actor(issuer, subject)` is a frozen value that checks the shape of the identity only: a non-empty `str` of at most 512 characters, with none of the Unicode categories `Cc` (controls), `Cf` (format characters such as U+202E and the zero-width joiner), `Zl` and `Zp` (U+2028 and U+2029) or `Cs` (lone surrogates). Other text, including combining marks, spaces and non-Latin scripts, is accepted and stored unchanged. It does not claim that a token was verified or that the identity is authentic; M1E establishes that. `actor=None` records an unauthenticated event with both actor columns NULL.
- **Identifiers:** `production_id`, and an `object_id` whose `object_type` is production, engagement or asset, must be exactly 32 lowercase hexadecimal characters, which is what the store generates and its `CHECK` constraints accept (no UUID version is required). A subject's `object_id` must be a canonical positive decimal integer string: ASCII digits, no sign, leading zero or whitespace, at most 9223372036854775807. An `object_id` requires an `object_type`, and `object_id=None` stays valid. A value that does not match raises before any SQL runs. Nothing is truncated, trimmed, case-folded or normalised, and a rejected value is never echoed in an error message. For a malformed or oversized external identifier, the handler records `object_id=None` with `AuditReason.INVALID_IDENTIFIER`, so the record never holds a valid-looking identifier that the client did not send.
- **Limits:** since M1D-3b (AM-13), application connections cannot update or delete audit rows, but they can still insert them with SQL directly, so the validation in `record_event` applies only to code that calls it. The table is not tamper-evident.

**AM-13: M1D-3b connection hardening (2026-11-03).** Approved design for the connection part of M1D-3, implemented in `store.py`. M1D-3 is now complete; M1E is the next milestone.
- **Schema check:** `connect()` checks `user_version` first, then compares every row of `sqlite_master` (type, name, table and definition text, including internal objects such as `sqlite_sequence` and the automatic indexes) with a reference built by running the `_SCHEMA` statements in a scratch in-memory database. A missing, added or modified object, or a version-1 database with an empty or foreign schema, raises `SchemaIntegrityError`. The message names objects by type and name only, is bounded and has control characters escaped; it never contains a definition. The connection is closed before the error propagates, so no usable connection is returned. `initialise_schema` keeps its own connection, with no authorizer, and is still the only code that creates objects. When the database is already at version 1 it runs the same schema check before returning, so a damaged version-1 database raises `SchemaIntegrityError` there too; nothing is repaired or adopted. There are no migrations.
- **Authorizer:** `connect()` installs it on the connection it returns, after the schema check. It is default-deny and decides by SQLite action code and object name, never by SQL text. It permits `SELECT`, reads, transactions, savepoints, recursive queries, every function except `load_extension`, a bare read of three pragmas (`foreign_keys`, `user_version`, `busy_timeout`), `INSERT`, `UPDATE` and `DELETE` on the business tables, and `INSERT` on `audit_events`. It refuses all DDL (create, drop and alter of tables, indexes, triggers, views and virtual tables, including temporary ones), `ATTACH`, `DETACH`, `ANALYZE`, `REINDEX`, `VACUUM`, every other pragma and any pragma given a value or argument (so foreign-key enforcement, `writable_schema`, `trusted_schema`, `recursive_triggers`, `ignore_check_constraints` and `user_version` cannot be changed), `UPDATE` and `DELETE` on `audit_events`, every write to a `sqlite_*` table, `load_extension`, and any action code not listed here.
- **Layers:** the audit and revocation triggers are unchanged. `INSERT OR REPLACE` on `audit_events` is an `INSERT` to the authorizer and is still stopped by the collision-guard trigger. Updates and deletes on the business tables are left to the schema (constraints, foreign keys and triggers) rather than to the authorizer.
- **Source guard:** `tests/guards/test_connections.py` fails if any module under `src/` other than `store.py` opens a SQLite database, so every application connection passes through `connect()`.
- **Limits:**
  - The authorizer governs the connections `connect()` returns. Code that holds a connection can replace its authorizer, and code that opens the file some other way is not governed.
  - The schema check detects schema drift at the moment a connection is opened. It does not watch an open connection, and it does not detect changes to data.
  - Replacing the database with another valid copy, including an older one, is not detected.
  - These measures do not make audit records cryptographically tamper-evident or tamper-proof. Anyone who can write the file can change rows and put the triggers back exactly as they were, and the next `connect()` accepts the result.
  - The authorizer does not see work SQLite does implicitly (the delete inside `INSERT OR REPLACE`, upkeep of `sqlite_sequence`, foreign-key actions), so the triggers remain necessary.
  - Complete audit coverage of every mutation must be verified separately in each workflow (M1F onwards).

**AM-14: M1E architecture and the M1E-0 dependency foundation (2026-11-03).** Approved by the security reviewer. M1E is split into M1E-0 (dependencies), M1E-1 (trusted configuration) and M1E-2 (the verifier and its tests). M1E-0 and M1E-1 are committed and M1E-2 is implemented (AM-15, AM-16). The first group below is the approved design: the trusted-keys bullet was built as M1E-1 and the rest as M1E-2.

*Approved design (built as M1E-1, AM-15, and M1E-2, AM-16):*
- **Algorithm and profile:** ES256 only (ECDSA P-256 with SHA-256). A restricted educational access-token profile: the JWS header may hold only `alg` (exactly `ES256`), `typ` (exactly `at+jwt`) and `kid`. Key URLs (`jku`, `x5u`), embedded keys (`jwk`, `x5c`), `crit` and every other header member are rejected. The profile borrows the `at+jwt` type from RFC 9068 and does not claim full RFC 9068 conformance.
- **Trusted keys** (amends the single-key wording in §4 and Addendum §5.5): a locally configured JWKS of one to eight public P-256 keys, so that keys can overlap during rotation. Each key needs a unique, bounded `kid`. The loader checks the key type and curve, checks that the point is valid, and rejects private key material and invalid, duplicate or conflicting metadata. The app refuses to start when the set is missing, unreadable, empty or invalid. Keys are never fetched, `PyJWKClient` is not used, the token header never chooses a key source, and a missing or unknown `kid` is rejected rather than trying every key.
- **Claims:** `iss` must equal the configured issuer string exactly. `aud` must be one string equal to the configured audience; a list is rejected. `sub`, `iss`, `aud`, `exp`, `iat` and `nbf` are required, and `sub` must pass the `Actor` shape rules.
- **Time:** zero clock skew (a lab assumption). The verifier reads the injected clock once per authentication attempt. `exp`, `iat` and `nbf` must be JSON integers, never booleans, within reasonable bounds. `now >= exp` means expired. `nbf` and `iat` may not be in the future, `exp > iat`, `nbf < exp`, and `exp - iat <= 600` seconds (A10, a lab assumption). Whole seconds are compared with the clock's microseconds by integer arithmetic. PyJWT's own time checks may be switched off only once these checks exist and are tested; signature verification is never switched off.
- **Identity versus permissions:** a successful verification yields only the verified issuer and subject. Role, production and scope claims are never used to authorise anything. The verifier stays independent of HTTP routes until M1F, which wires it to FastAPI and adds the authentication-denial audit vocabulary. An in-process sentinel or source guard can discourage accidental construction of a verified identity; it is not a security boundary against malicious Python code.

- **Lock scope:** CPython 3.13 on macOS arm64 only. `pydantic_core`, `cffi` and `cryptography` are the platform-specific wheels; the lock holds one file for each (`cffi` has 99 files and `cryptography` 58 on PyPI for these versions). Dry-runs for CPython 3.12 on macOS arm64 and CPython 3.13 on Linux x86_64 were refused on a hash mismatch, re-run on 2026-11-03 against the 23-entry lock. Other platforms need their own lock, generated and verified there.
- **Advisories, 2026-11-03:** OSV and PyPI's own `vulnerabilities` field list none for the four exact versions. Limits: this is a lookup, not a scan; the databases lag; and OSV's PyPI records may not cover the OpenSSL that the `cryptography` wheels bundle. History: OSV holds 24 GHSA advisories for PyJWT, 21 of them fixed in 2.12.0 to 2.15.0 (one, whose affected range is 2.11.0 to 2.13.0, ends before 2.15.1), and 42 records for `cryptography`. Most PyJWT advisories concern `PyJWKClient`, `PyJWK`, HMAC keys and PEM detection, which M1E-2 does not call. Repeat the lookup before M1E-2 is committed.
- **Runtime compatibility, verified in a fresh venv on CPython 3.13.7, macOS arm64:**
  - The locked wheels installed with `--require-hashes --only-binary=:all:`, then `pip install --no-deps -e .`. `pip check` was clean, and the environment held the 23 locked distributions plus `pip` and the editable project, nothing else. Every artifact was a `.whl` from `files.pythonhosted.org`.
  - A one-digit change to a hash, a lock without `cffi`, and a lock without `pycparser` were each refused by pip with nothing installed. Removing `pycparser` from an otherwise complete environment failed `pip check` and both environment tests.
  - An ephemeral in-memory P-256 key signed a synthetic ES256 token. It verified with only the public key and an `["ES256"]` allow-list. A changed payload, a flipped or truncated signature, a different public key, an `ES384`-only allow-list and an unsigned token were each rejected. No key was written to disk.
- **V2 findings for PyJWT 2.15.1** (source read at the 2.15.1 tag, and each behaviour run in that venv):
  - `decode` requires an `algorithms` argument and has no clock parameter: its time checks use the real clock, so M1E-2 does its own with the injected clock.
  - With its own checks on, PyJWT accepts `exp`, `iat` and `nbf` given as numeric strings or floats, because it applies `int()`, and reads `true` as 1. M1E-2 therefore checks their JSON types itself.
  - `require` treats an absent or `null` claim as missing. `iss` is compared by exact string equality. `strict_aud` rejects a list-valued `aud`; without it a list that contains the audience is accepted.
  - An unknown `crit` extension and a non-string `kid` are rejected. A `jku` header is ignored, not rejected, so M1E-2 must reject unexpected header members itself.
  - ES256 verification accepts a private key object as the key. The key loader must therefore reject private material, and only public key objects are passed to PyJWT.
  - Reusing an options dictionary across calls did not weaken a later verification in 2.15.1 (the CVE-2026-103001 pattern, which affects 2.11.0 to 2.13.0). M1E-2 still builds a fresh dictionary for every call.
- **Unchanged:** the build-backend limitation recorded in AM-9 (the `setuptools` artifact is not hash-verified), the single-platform scope, and the exclusion of `fastapi[standard]` and every other package.

**AM-15: M1E-1 trusted configuration (2026-11-03).** Approved by the security reviewer. Implemented in `settings.py`. It configures trust and authenticates nothing: it never sees a token, and the verifier (M1E-2) has not started.
- **Loader:** `load_settings(config_path: Path) -> TrustedSettings` reads a TOML settings file and the key-set file it names. Any missing, unreadable, oversized or invalid input raises `ConfigurationError`. It reads no environment variable and no command-line argument, and it uses no network. A `str` instead of a `Path` raises `TypeError`.
- **Settings file** (TOML, at most 8,192 bytes, exactly three members): `issuer` and `audience`, each 1 to 512 visible ASCII characters with no spaces (so no control, format, separator or non-ASCII characters), and `jwks_path`, 1 to 1,024 characters with no control characters and not a URL. An absolute `jwks_path` is used as given. A relative one is resolved against the directory of the settings file as the caller named it, and never against the working directory. Symbolic links are not resolved. A relative settings path is relative to the working directory at the call, as any relative path is.
- **Key set** (JSON, at most 16,384 bytes), a restricted educational profile and not a general JWKS parser: an object whose only member is `keys`, a list of one to eight objects. Each key has exactly `kty` `EC`, `crv` `P-256`, `kid`, `x` and `y`, and may also carry `use` `sig` and `alg` `ES256` with exactly those values. A `kid` is 1 to 64 characters of `A-Z a-z 0-9 . _ -`, unique, compared exactly and case-sensitively. `x` and `y` are canonical unpadded base64url, 43 characters for 32 bytes, with no stray trailing bits, and together a point that `cryptography` accepts on P-256. Refused: private-key members (`d` and the RSA and symmetric ones), other key types and curves, every other member (including `jku`, `x5u`, `x5c`, `x5t` and `key_ops`), repeated member names anywhere in the file, `NaN` and `Infinity`, a byte order mark or invalid UTF-8, zero or more than eight keys, and the same public key under two kids.
- **Result:** a frozen `TrustedSettings(issuer, audience, public_keys)` whose `public_keys` is a read-only copy (`MappingProxyType`) of `kid` to `cryptography` P-256 public key. The class validates its own arguments with the same rules, so a directly built instance cannot hold a private key object, a key of another curve, more than eight keys or a bad `kid`.
- **Errors:** a message names the file and the rule that failed, and the 1-based position of a key. It never repeats file content, a member name or value from a file, a `kid`, a coordinate or any key material.
- **Limits:**
  - A `kid` that matches means nothing until M1E-2 verifies a signature with that key. The loader selects no key and checks no token.
  - Both files are trusted local configuration. The loader does not check their permissions or ownership, and it cannot tell whether someone who can edit them has changed who is trusted. The files are read once per call; there is no reload or rotation tooling, so a change needs a new load.
  - The two files are read one after the other, so they can change between the reads. The size limit comes from a bounded read, not from a separate size check.
  - `cryptography` decides whether a point is valid. The loader does not check that a key belongs to the issuer or is within any validity period.
  - Review choices: optional `use` and `alg` are accepted, the same key under two kids is refused, and issuer and audience are limited to visible ASCII. All the numeric bounds are lab assumptions.
- **Tests:** `tests/test_settings.py` generates its keys in memory and writes only public coordinates. Each check was removed in turn from a scratch copy of `settings.py`, and the tests failed every time (26 variants).

**AM-16: M1E-2 cryptographic identity verification (2026-11-03).** Approved by the security reviewer. Implemented in `identity.py`; it completes M1E. It authenticates a bearer token and authorises nothing. No route, HTTP object, database or engagement lookup is involved (M1F).
- **Interface:** `authenticate(authorization: str | None, settings: TrustedSettings, clock: Clock) -> VerifiedIdentity`, with everything injected. `None` is refused as missing credentials. It reads no environment variable or command-line argument, fetches no key, opens no database and takes no request object. Every refusal raises one exception, `AuthenticationError`, whose `reason` is a member of the closed `AuthFailure` vocabulary (11 members) for logs and audit. The message holds the reason only, never any part of the token. A clock that returns a naive time raises its own `ValueError`: that is a fault of the server, not of the credentials.
- **Result:** `VerifiedIdentity(issuer, subject)`, frozen, with no role, production or scope, and `as_actor()` to the existing audit `Actor`. Building one takes a module-private sentinel, so it needs a deliberate act, and `authenticate()` is the only code that does it. `tests/guards/test_token_minting.py` flags any other use in `src/`. Neither is a security boundary: code running in the process can import the sentinel, and no static check sees every way of signing.
- **Header and key:** the value is `Bearer`, one ASCII space and a compact JWS of at most 4,096 bytes with three non-empty, canonical base64url segments. The header holds exactly `alg` `ES256`, `typ` `at+jwt` and a `kid` of 1 to 64 characters; duplicate member names and every other member (`jku`, `jwk`, `x5u`, `x5c`, `crit`, `b64` and the rest) are refused. The `kid` selects one configured public-key object by exact comparison. An unknown `kid` is refused and no other key is tried.
- **PyJWT's part:** one call to `jwt.decode` with that key object, `algorithms=["ES256"]`, the configured issuer and audience, `strict_aud`, and the six claims required (`iss`, `sub`, `aud`, `exp`, `iat`, `nbf`). Signature, issuer, audience and required-claim checks stay on. Only its `exp`, `nbf` and `iat` checks are off, because they use the real clock. The options dictionary is new for every call. `iss` and `aud` are then compared again, exactly, and `sub` must satisfy the `Actor` shape rules. Extra claims are ignored and never read; a `jti`, if present, must be a string (PyJWT's check, left on) and is otherwise unused. Once PyJWT has verified the token, and before any claim value is read, the signed payload is parsed again strictly with the helpers used for the header. A repeated member name at any depth, or a `NaN` or `Infinity` anywhere (extra claims included), is refused as `invalid_claims`, so the identity cannot depend on which member another parser would pick. RFC 7519 allows PyJWT's last-member reading; this profile does not.
- **Time:** the injected clock is read once per attempt, first. `exp`, `iat` and `nbf` must be JSON integers, never booleans, strings or floats, between 946,684,800 (2000-01-01) and 4,102,444,800 (2100-01-01). They must satisfy `exp > iat`, `nbf < exp` and `exp - iat <= 600`. There is no clock skew. A token is expired when `now >= exp`, and not yet valid while `now < nbf` or `now < iat`. Whole seconds are multiplied by 1,000,000 and compared with the clock's microseconds as integers.
- **Tests:** `tests/support/token_issuer.py` makes ephemeral keys in memory and builds tokens from raw JSON, signing with `cryptography` directly, so the verifier is tested on tokens PyJWT did not produce. Nothing is written to disk. `tests/test_identity.py` (329 tests) asserts the exact reason for every refusal, the boundaries to the microsecond, that fabricated role, scope and production claims change nothing, and that properly signed payloads with repeated member names or non-finite numbers are refused while ordinary extra claims still authenticate (a control shows PyJWT alone accepts every one of those payloads). `tests/guards/test_token_minting.py` (36 tests) holds the source guard and a scan for committed private-key headers. Each check in `identity.py` was removed in turn from a scratch copy: the tests failed for 37 of 42 variants, and the other five are equivalent because PyJWT or the bounds check enforces the same rule (the algorithm pre-check, the signature and payload canonical checks, the issuer re-check and the boolean type check). Thirteen violations injected into a scratch tree each failed the guard.
- **Limits:**
  - A verified token shows only that the holder of a configured key's private half issued it, with these claims, within its lifetime. There is no replay protection (`jti` is not tracked), no way to revoke a token before it expires, and no binding to a client. Anyone who holds the token can use it until `exp`, and the lifetime cap (600 seconds, a lab assumption) is the only limit.
  - Zero skew means any difference between the issuer's clock and the server's can refuse a valid token or accept an expired one.
  - `sub` is accepted as the issuer gave it, after shape rules only. Whether that subject has access is the engagement lookup in M1F.
  - The strict payload parse is a second parse of the same bytes. It rejects ambiguity but does not validate the shape of extra claims, which are ignored.
  - Signature and payload parsing rely on PyJWT 2.15.1 and `cryptography` 50.0.2. Repeat the advisory lookup whenever either changes.
  - `AuthFailure` reasons are for logs and audit. M1F must not show them to a client. The audit reason `invalid_credentials` for a failed authentication was added in M1F-1 (AM-17), so the detail never needs recording.

**AM-17: M1F authorisation (2026-11-04).** Approved by the security reviewer. M1F is split into M1F-1 (pure server-side engagement authorisation, implemented in `authz.py`), M1F-2 (the first authenticated, authorised and audited route) and M1F-3 (coordinator engagement creation and revocation). M1F-1 was the first to be implemented; M1F-2 is AM-18.
- **First route (M1F-2, implemented: AM-18):** `GET /productions/{production_id}/engagement` returns only the caller's own engagement for that production. Every authorisation denial in M1F is a generic 403; the missing-versus-forbidden rule for assets is defined in M1G. Authentication failures are a generic 401 that never shows an `AuthFailure` value.
- **No implementation selector:** the normal application `Dependencies` gets no injectable authorisation implementation, and the application uses the reference authoriser. Deliberately vulnerable implementations belong under `labs/` in the designated findings milestone, and an exploit test may call a reference and a vulnerable function explicitly in a test-only harness, never through a runtime switch.
- **Decision instant and ordering (M1F-2):** open a SQLite connection in the synchronous handler; take `store.transaction()` (`BEGIN IMMEDIATE`); read the clock once, after the transaction is held; authenticate with that instant; authorise with the same instant and the transaction's live view; record the audit event in the same transaction; commit; then respond. A request that waited for the lock therefore never decides on a stale timestamp, and ordering against a revocation is deterministic: a revocation that committed before the request began is seen, and one that waits for the lock is not. The cost is that authenticating while holding the SQLite writer lock serialises every request. That is acceptable for this educational lab and is not a recommendation for a general service.
- **Interface (M1F-1):** `authorize_engagement(conn, identity, production_id, action, now_micros) -> AuthorizedEngagement`. It accepts only a `VerifiedIdentity`, an `Action`, an `sqlite3.Connection` and an `int` instant (a `bool` is refused); a wrong type raises `TypeError` and a call outside a transaction raises `StoreError`. It reads no clock, no environment variable, no configuration and no token claim, opens no connection, and never commits or rolls back. It issues one parameterised `SELECT` that joins `subjects` and `engagements` and matches `issuer`, `subject` and `production_id` exactly; it never queries the productions table.
- **Policy:** two closed actions. `view_own_engagement` is permitted to the `coordinator` and `vendor` roles; `manage_engagements` (for M1F-3) to the `coordinator` only. A role that is not in the table may take no action. The role, the end date and the revocation come only from the `engagements` row.
- **Denial order:** an invalid production identifier (not 32 lowercase hex characters, or not a `str`); no matching subject or engagement; revoked (`revoked_at` set); expired (`now_micros >= ends_at`); the role lacks the action. An unknown production and a production with no engagement give the same reason, `no_engagement`. Each denial is an `AuthorizationDenied` carrying one of five `AuditReason` members, and the exception message holds only that reason.
- **Result:** an immutable `AuthorizedEngagement(engagement_id, role, ends_at)`, with `ends_at` in microseconds. Building one takes a module-private sentinel, like `VerifiedIdentity`; this discourages accidents and is not a security boundary.
- **Audit vocabulary:** two members were added to the closed sets, `AuditAction.ENGAGEMENT_VIEWED` (`engagement.viewed`) and `AuditReason.INVALID_CREDENTIALS` (`invalid_credentials`). `authz.py` records nothing: the route records one event per request in the same transaction.
- **Tests:** `tests/test_authz.py` (84 tests) uses identities produced by the real verifier and a real SQLite file. Each check was removed in turn from a scratch copy of `authz.py` (31 variants) and the tests failed every time.
- **Limits:**
  - `authorize_engagement` can see that a transaction is open, not that it is `BEGIN IMMEDIATE`. The ordering guarantee above holds only if the caller uses `store.transaction()`; M1F-2 must do so and test it.
  - It decides for the caller's own engagement in one production. Another principal's engagement, and the effect of a vendor's revocation or expiry on a coordinator's acceptance of its deliveries (A9), are M1J.
  - The policy table is small by design and grows with later actions; each addition is a reviewed change.
  - A valid token proves identity only. A revoked or expired engagement stays denied while the same token keeps authenticating until its `exp`.

**AM-18: M1F-2 first authenticated route (2026-11-04).** Approved by the security reviewer. Implemented in `engagements.py` and registered in `app.py`. It is reference behaviour only: it has no vulnerable variant (F-06 is a later findings slice) and no way to create or revoke an engagement (M1F-3).
- **Route:** `GET /productions/{production_id}/engagement` returns the caller's own role and engagement end time (UTC ISO 8601, microseconds, `Z`) and nothing else. Every response the handler produces (200, 401, 403, 500 and 503) carries `Cache-Control: no-store`, because each is personal to the caller; that header is the whole caching policy and there is no HTTP-security middleware. It is registered with `add_api_route` in `create_app`: FastAPI 0.141.1 wraps `include_router` in a private `_IncludedRouter` that hides the route from `app.routes`, and an allowlist test should not depend on a private class. The path uses the `:path` converter, so any text between the fixed segments is an identifier to refuse with a 403, not a missing page. The one exception is a newline, which the converter's `.*` does not match: that request finds no route and gets a 404 before the handler, with no audit event.
- **Dependencies:** a frozen `settings: TrustedSettings`, `clock: Clock` and `database_path: Path`, each type-checked, and no other field. There is no authorisation function to inject, no selector and no use of `dependency_overrides`. `create_app` builds a new endpoint for each app, so two apps share no state, and `engagements.py` has no mutable module-level state (a test reads the source).
- **Request order, one SQLite write transaction:** open `store.connect()` in the handler thread; `store.transaction()` (`BEGIN IMMEDIATE`); read the clock once; authenticate; authorise; append one audit event; commit; respond. The instant goes to `authenticate` and `record_event` as a fixed-instant adapter that reads no clock, and to `authorize_engagement` as integer microseconds from `to_micros`. The calls go through their modules (`identity.authenticate`, `authz.authorize_engagement`, `audit.record_event`, `store.connect`, `store.transaction`) so that tests can watch the order. Verifying a signature while holding the writer lock is the simplification recorded in AM-17; it is not a pattern for a scalable service.
- **Authentication:** only the one `Authorization` header counts. A missing, repeated or refused credential is a 401 with `WWW-Authenticate: Bearer` and one fixed body, whatever the `AuthFailure`. Identity comes from nowhere else: not `X-Authenticated-User`, `X-Forwarded-User`, a cookie or a token role claim. A failed authentication outranks a bad path.
- **Authorisation:** `authorize_engagement` with `view_own_engagement`. Every refusal (invalid identifier, unknown production, no engagement, revoked, expired) is the same 403 with the same body; the reason goes only to the audit record.
- **Audit, one event per decided request, committed with the decision:** a success is `engagement.viewed` / `allowed` with the verified actor, the requested production and the authorising engagement as the object. A refusal is `access.denied` / `denied` with the actor and the `AuditReason`; the production is recorded only if it passed the identifier check, so an invalid identifier is never recorded as an object. An authentication failure is `access.denied` / `denied` / `invalid_credentials` with no actor and no production, and never the token or the `AuthFailure`. The guarantee covers the decisions the handler makes. An unmatched path and the framework's own 404 and 405 answers run no handler, so they are outside it: they are not audited, decide nothing and do not carry the `Cache-Control` header.
- **Failure:** an error while deciding, recording or committing rolls the transaction back and gives a generic 500, logged with its traceback and never returned. A `SQLITE_BUSY` or `SQLITE_LOCKED` error anywhere in the request, including a lock not acquired within `BUSY_TIMEOUT_SECONDS`, gives a generic 503. Nothing is decided in either case. A database that cannot be opened cannot record anything, so such a request is not audited. The `except Exception` at the handler boundary is the only broad catch; it logs and converts the failure into a refusal.
- **Tests:** `tests/test_engagements_api.py` (139 tests) drives the real application through the TestClient, with a SQLite file per test and ephemeral keys. Request/revocation interleavings, in both orders, use thread events and no sleeps. `tests/test_app.py` (28) covers the factory contract. Each check was removed in turn from a scratch copy of `engagements.py` or `app.py` (40 variants) and the tests failed every time; a naive handler that trusts a header and an unverified token's claims fails 120 of the 167 tests.
- **Limits:**
  - Every request that reaches the handler takes the writer lock and appends one audit row, authenticated or not, so anonymous traffic can grow the audit table and occupy the lock. Rate limiting, retention and size limits are out of scope for the lab.
  - Framework-generated answers (an unmatched path, a path containing a newline, a method other than GET) are outside the one-audit-event-per-handler-decision guarantee: no handler runs, so nothing is audited and no `Cache-Control` header is added.
  - The request flow described above lives in `request_flow.py` since M1F-3A (AM-19), so that the management routes share one order. `engagements.py` keeps only the path, the action and the view operation.
  - The 500 and 503 answers are logged, not recorded in the audit table.

**AM-19: M1F-3 approved in two stages; M1F-3A implemented (2026-11-04).** Approved by the security reviewer. The four stages proposed after M1F-2 are consolidated into M1F-3A (the shared request flow and a production-scoped revocation function, implemented here) and M1F-3B (the coordinator creation and revocation routes, not started). M1F-3A adds no route and changes no behaviour of the existing one.
- **Decisions for M1F-3B:**
  - Creation and revocation are both `POST` and need the `manage_engagements` action, which only coordinators have.
  - A coordinator may create coordinator engagements, revoke other coordinators and revoke itself. There is no last-coordinator safeguard in this MVP, so a production can be left with no coordinator. Recovery is out of band: someone with access to the database file adds an engagement through the store. The API has no way to do it.
  - A missing target engagement and one that belongs to another production give the same generic 403.
  - A repeated revocation returns an idempotent 200 with the original revocation time.
  - The subject must already exist in `subjects`, and its issuer is the verified caller's issuer. There is no identity-provisioning or invitation system.
  - The expiry is mandatory, UTC, strictly later than the decision instant and at most exactly 90 days (7,776,000,000,000 µs) after it.
  - An expired or revoked engagement cannot be recreated or renewed through this MVP.
- **Audit policy for M1F-3B** (this replaces the proposal that authorised-but-rejected requests and repeated revocations leave no event):
  - Closed vocabulary to add in M1F-3B: actions `ENGAGEMENT_REVOKE_REPEATED` (`engagement.revoke_repeated`) and `ENGAGEMENT_REQUEST_REJECTED` (`engagement.request_rejected`); reasons `INVALID_REQUEST` (`invalid_request`), `ENGAGEMENT_EXISTS` (`engagement_exists`) and `PAYLOAD_TOO_LARGE` (`payload_too_large`).
  - A repeated revocation is recorded with `Outcome.RECORDED` and is never described as a new revocation. A management request rejected after authentication and authorisation (a validation error or a duplicate) is recorded with `Outcome.DENIED`.
  - No unvalidated subject string, request body or other user text goes into an audit reason or any other column.
  - The rule is one audit event for each completed, committed management-handler decision: 200, 201, 400, 401, 403, 409 and 413 where they apply. A database failure that prevents the commit cannot be audited in the same database. Framework 404 and 405 answers stay outside the rule (AM-18).
- **Body handling for M1F-3B:** an asynchronous reader takes the body, bounded, before the SQLite transaction, so a slow client cannot hold the writer lock. It limits the bytes actually streamed, not only `Content-Length`, stops buffering at the cap and returns an oversized indicator. The synchronous handler still authenticates and authorises first, and only then answers 413 and records the rejection, so an invalid credential gets the generic 401 and an unauthorised caller the generic 403 whatever the body holds. Nothing of this reader is in M1F-3A.
- **`request_flow.py` (M1F-3A):** the order of AM-18 moved out of `engagements.py` unchanged: open the connection in the handler thread, `BEGIN IMMEDIATE`, read the clock once, authenticate on that instant, authorise the action in the URL's production on it, run the endpoint's operation, which records its audit event, commit, then respond with `Cache-Control: no-store`. An endpoint supplies the action and an operation taking a `Context` (connection, the fixed-instant clock, the instant in microseconds, the caller, its grant, the production). The authentication and authorisation denial events, the answers and the failure handling are in the flow, so an endpoint cannot forget or reorder them. There is no middleware, registry or selector. The existing `GET` has the same statuses, bodies, headers, audit rows, SQL order and failure behaviour; the only change visible outside is that a failure is logged by the logger `content_boundary_lab.request_flow` instead of `content_boundary_lab.engagements`, with the same messages. Tests: `tests/test_engagements_api.py` (148 tests) now also checks that the flow reads the clock exactly once, that `engagements.py` calls none of the flow's primitives, and, with a stand-in operation, that the flow authorises the action it is given, runs the operation only after both checks, inside the transaction and on the one instant, and rolls everything back if the operation fails. A scratch run removed one safeguard at a time (29 variants: 11 of the scoped function and its guard, 18 of the flow's order, answers and headers) and the tests failed every time.
- **`store.revoke_engagement_in_production(conn, production_id, engagement_id, now_micros) -> Revocation`:**
  - It binds the engagement id and the production id in the one `UPDATE` that mutates, with `revoked_at IS NULL`, so an engagement of another production is never reached. It returns `REVOKED`, `ALREADY_REVOKED` (with the original time) or `NOT_FOUND`. A missing id and another production's id give the identical `NOT_FOUND`, even if the other engagement is already revoked.
  - It needs an open caller-owned transaction (`StoreError` otherwise), validates both ids as 32 lowercase hexadecimal characters (`TypeError` or `ValueError`, before any SQL, never echoing the value), requires an `int` instant that is not a `bool`, reads no clock, and never commits or rolls back.
  - If the `UPDATE` changes no row but the engagement exists and is not revoked, it raises `StoreError` rather than report a repeat.
  - It does not authorise anyone. The route must authorise the caller for the same production in the same `BEGIN IMMEDIATE` transaction, then call it.
  - `tests/test_scoped_revocation.py` (58 tests) runs against the real hardened store, including an ALPHA coordinator authorised by the real verifier and `authz` who cannot revoke BRAVO's engagement under ALPHA's production id.
- **The unscoped `store.revoke_engagement(conn, clock, engagement_id)`** is kept because 21 test call sites use it, and its docstring now says it is unsuitable for request-controlled ids. `tests/guards/test_revocation_scope.py` (21 tests) fails if any module under `src/` other than `store.py` references it as an attribute, name, import, star import or string. It does not see a name built at run time. A test shows that the unscoped function does revoke another production's engagement, so that the contrast stays on record; it is deleted with the function when the call sites are migrated.
- **Limits:** the scoped function is only as strong as the transaction around it: a caller that authorises outside its `BEGIN IMMEDIATE` could be raced by a revocation, and the function cannot tell. The 90-day cap, the audit vocabulary, the body reader and both routes are M1F-3B (AM-20).

**AM-20: M1F-3B coordinator management routes (2026-11-04).** Approved by the security reviewer. Implemented in `management.py`, with `request_flow.py` (body support and the audit count check), `audit.py` (vocabulary) and `app.py` (registration). It completes M1F. It adds no identity provisioning or invitation: a subject must already exist.
- **Routes** (both use the flow of AM-18 and AM-19 and the action `manage_engagements`, which only an active coordinator engagement in the URL's production grants):
  - `POST /productions/{production_id}/engagements` creates an engagement and answers 201 with `engagement_id`, `subject`, `role` and `ends_at` (UTC, microseconds).
  - `POST /productions/{production_id}/engagements/{engagement_id}/revoke` takes no body and answers 200 with `engagement_id`, `status` (`revoked`) and `revoked_at` (UTC, microseconds).
  - Both use the `:path` converter, so malformed identifiers are refused with a 403 rather than a 404. Every response carries `Cache-Control: no-store`.
- **Create:** the body is a JSON object with exactly `subject`, `role` and `ends_at`.
  - The subject must already exist under the caller's own verified issuer (never one from the body) and is looked up exactly. The role is `vendor` or `coordinator`. `ends_at` is `YYYY-MM-DDTHH:MM:SS[.f to ffffff]Z` and nothing else, and keeps its microseconds.
  - `now < ends_at <= now + 90 days` on the one captured request instant. 90 days is exactly 7,776,000,000,000 µs, the cap itself is accepted and the cap plus one microsecond is not. `created_at` is that instant.
  - Any existing `(subject, production)` engagement, active, expired or revoked, is a 409. There is no renewal and no re-engagement.
  - An unknown subject, a subject that exists only under another issuer, and every malformed field are a 400 `{"detail":"Invalid request","field":...}` where `field` is one of `body`, `subject`, `role` and `ends_at`. Nothing of the input is echoed.
  - A repeated JSON member, NaN, Infinity, an unexpected member, a missing member or invalid UTF-8 is a 400 on `body`. The production and issuer are never read from the body: naming them is an unexpected member.
- **Revoke:** `store.revoke_engagement_in_production(conn, production_id, engagement_id, now_micros)`, in the same `BEGIN IMMEDIATE` transaction as the coordinator's authorisation, with the production from the URL. A missing target, a target in another production and a malformed id are the same generic 403. The audit reasons differ: `not_found_or_forbidden` for a well-formed id (recorded as the object) and `invalid_identifier` for a malformed one (not recorded as an object). A repeat answers 200 with the original `revoked_at`. The unscoped `store.revoke_engagement` is not called by any route (the guard of AM-19 and a test).
- **Coordinator powers:** coordinators may create coordinators, revoke other coordinators and revoke themselves. **There is no last-coordinator safeguard.** Revoking the last coordinator of a production leaves nobody who can manage it through the API; the recovery assumption is out of band, by someone with access to the database file adding an engagement through the store. A test records this.
- **Audit vocabulary added:** actions `ENGAGEMENT_REVOKE_REPEATED` (`engagement.revoke_repeated`) and `ENGAGEMENT_REQUEST_REJECTED` (`engagement.request_rejected`); reasons `INVALID_REQUEST`, `ENGAGEMENT_EXISTS` and `PAYLOAD_TOO_LARGE`. One event for each committed decision:
  - 201: `engagement.created` / `allowed`, with the new engagement as the object.
  - A new revocation: `engagement.revoked` / `allowed`. A repeat: `engagement.revoke_repeated` / `recorded`, never described as a revocation.
  - 400, 409 and 413 after authentication and authorisation: `engagement.request_rejected` / `denied` with `invalid_request`, `engagement_exists` or `payload_too_large`, the actor and the URL's production, and no object.
  - 401 and 403: `access.denied` / `denied`, as before.
  - Nothing from the request body, no subject string, no token and no field value is stored or logged.
- **The audit count check (`request_flow.py`):** after reading the clock the flow reads `MAX(seq)` of `audit_events`; after the operation, and before the commit, it counts the events with a greater `seq`. Anything but one raises `AuditCountError`, the transaction rolls back and the answer is the generic 500. The writer lock makes the count exact. The existing `GET` is unchanged apart from these two `SELECT`s in its SQL trace.
- **The body (`request_flow.read_body`):** an `async` dependency that reads at most 4 KiB of the streamed bytes in the event loop before the handler, so before `BEGIN IMMEDIATE`, and stops pulling after the chunk that crosses the limit. It never looks at `Content-Length`. It flags an oversized body and decides nothing: the 413 is the operation's, after authentication and authorisation, so an invalid credential gets the generic 401 and an unauthorised caller the generic 403 whatever the body holds. No Pydantic body model is used, so the framework produces no 422 before authentication. The SQLite connection is still opened and used in the handler's own thread.
- **Tests:** `tests/test_engagement_creation_api.py` (136 tests), `tests/test_engagement_revocation_api.py` (46), the extended `tests/test_engagements_api.py` (155) and `tests/test_audit.py`; the HTTP harness moved unchanged to `tests/support/http_lab.py`, with two more seeded rows. Deterministic interleavings cover two simultaneous creations (one 201, one 409), two simultaneous revocations (one new, one repeat with the original time), a view that holds the lock before a revocation and one that waits behind it, and a creation queued behind its own coordinator's revocation. A scratch run removed one safeguard at a time (21 variants, for scope, role, the 90-day boundary, duplicates, issuer, body limits and precedence, audit kind and count) and the tests failed every time.
- **Limits:**
  - Every request that reaches a handler takes the writer lock and appends one audit row, including every rejected one, so authenticated coordinators and anonymous callers can grow the audit table and occupy the lock. Rate limiting and retention are out of scope.
  - A successful creation reveals that a subject exists, to a coordinator. Only a success does; there is no separate lookup.
  - An expired or revoked engagement blocks the same subject in the same production for good, and no route renews it.
  - If the injected clock reads earlier than an engagement's `created_at`, the schema's `revoked_at >= created_at` check fails the revocation and the answer is a 500, not a rejected request.
  - The 500 and 503 answers, and a request whose database cannot be opened, are logged but cannot be audited in that database.
  - Framework answers (an unmatched path, a path with a newline, an unsupported method) stay outside the one-event rule (AM-18).

**AM-21: M1G production-scoped asset read (2026-11-04).** Approved by the security reviewer in two stages. M1G-A (committed as `67debcd`) adds the policy action, the one-statement lookup and the download extension of the request flow, with no route; M1G-B adds `GET /productions/{production_id}/assets/{asset_id}`. It is the F-02 reference. Synthetic content only. M1H (ingest) does not start with it.
- **Authorisation:** a new action `READ_ASSET`, permitted to `coordinator` and `vendor` (D4: access is per production, not per object within it). The request flow authorises it for the production in the URL with the existing generic 403 answers and audit reasons, on the same instant and in the same transaction as everything else.
- **One authoritative lookup:** `assets.get_asset_in_scope(conn, caller, production_id, asset_id, now_micros)` is one parameterised `SELECT` that joins the asset to the caller's engagement through the asset's own `production_id`, and binds the requested asset id, the requested production id, the verified `(issuer, subject)`, `revoked_at IS NULL` and `ends_at > now_micros`. It does not authorise against the URL's production and then fetch an asset by id; there is no function that reads an asset by id alone, and `tests/guards/test_asset_scope.py` fails if any other SQL in `src/` reads, updates or deletes from `assets`, or if this statement loses a condition. Ids are validated (32 lowercase hexadecimal characters) before any SQL runs; `now_micros` must be an `int`, not a `bool`; the function reads no clock, writes nothing and neither commits nor rolls back. The role is the flow's decision, not the lookup's.
- **No asset state exists, and none is invented.** The `assets` table has `id`, `production_id`, `display_name` and `created_at`. M0's lifecycle states (`SEALING`, `SCAN_PASSED`, `ACCEPTED`, `PROMOTING`, `PROMOTED`, `INTEGRITY_FAILED`) belong to deliveries (M1H to M1K). A row in `assets`, with its bytes under the trusted root, is the readable set; quarantined or unapproved bytes live elsewhere and are never keyed by `assets.id`. When M1K adds states, the lookup gains the condition in the same statement.
- **Object-level misses** (an unknown asset, an asset of another production, a malformed id) get one generic `404 {"detail":"Not found"}`, byte-identical, via `request_flow.not_found`, recorded as `access.denied` / `denied` with `not_found_or_forbidden` (the well-formed id as the object) or `invalid_identifier` (no object). Production-level failures stay the flow's generic 403. This differs from the 403 for revocation targets (AM-20) on purpose: M0 F-02 names 404 for assets, and neither answer reveals whether an object exists elsewhere.
- **Download extension of the flow (`request_flow.py`):** a `Decision` may carry a `Download` (an open file, its size and the stored display name); a download is a plain 200 with no content and no headers of its own. The bytes are streamed after the commit, never inside the transaction, so a slow client cannot hold the writer lock. The flow sets every header: `Content-Type: application/octet-stream`, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`, `Content-Length` from the opened file and `Content-Disposition`. No `ETag`, `Last-Modified`, `Accept-Ranges` or URL is sent, and a `Range` request gets the whole file. `GET` is the only method; `HEAD` is a 405.
- **Failures are divided by the commit.** Before it (the operation, the audit count, the commit): roll back, close the file, answer the generic error, record no `asset.read`. After it: the committed event stays; the response closes the file in a `finally` around the whole ASGI call, so also when the client disconnects before the first byte, the send fails at the start or mid-stream, or the call is cancelled; once headers are sent no replacement response is attempted, and what the client observes of a transport failure is for the server and the connection to decide. A generator's own cleanup is not relied on: it does not run if the stream never starts (checked in a scratch run).
- **What `asset.read / allowed` means:** the caller was authenticated and authorised, the asset was in scope, the file was opened and the server committed to serve it. It is not evidence that any byte reached the client, and there is no completion event in M1G. A response already authorised is not cut off when authorisation is later withdrawn; only requests that begin after the revocation commits are refused (M0 §2: a started transfer may finish).
- **Download filename:** the display name stays unchanged in SQLite. `safe_download_filename` derives a separate name: control, format (including bidirectional and zero-width), unassigned, private-use and surrogate characters, line and paragraph separators, path separators, the Windows-reserved set, quotes, semicolons and percent signs become `_`; other space characters become a space; leading and trailing dots and spaces are removed; a Windows device name gets a leading `_`; the length is bounded to 100 with a short extension kept; an empty result is `download`. `content_disposition` builds the ASCII `filename` and the UTF-8 `filename*` from that one value, so the header is printable ASCII, one value, and cannot gain a parameter or a header.
- **Tests (M1G-A):** `tests/test_asset_lookup.py`, `tests/test_download_flow.py`, `tests/guards/test_asset_scope.py` and the policy rows of `tests/test_authz.py`. A scratch run removed one safeguard at a time (20 variants, for the lookup's conditions, the policy, closing, filename sanitising and headers) and the tests failed every time.
- **The route (M1G-B):** `GET /productions/{production_id:path}/assets/{asset_id:path}`, registered before the engagement `GET` so that an asset id such as `engagement` is an asset miss. The operation validates the asset id (a malformed id is never looked up and never recorded as an object), calls `get_asset_in_scope`, opens the file, records `asset.read` / `allowed` with the asset as the object, and returns the open file to the flow. The order in the transaction is: clock, authentication, the flow's authorisation of `READ_ASSET`, the lookup, the file opening, the audit event, the count check, the commit; the bytes go out afterwards. `HEAD` and every other method are a 405, and a `Range` header gets the whole file.
- **The trusted asset root:** `Dependencies` gains `asset_root`, an absolute `Path` (a relative one is refused at app creation, because it would depend on the working directory). It is the application's one read-only storage boundary. Quarantine is a different directory that the application is not configured with. The storage convention is flat: an asset's bytes are the file named by its id. The id is 32 lowercase hexadecimal characters (the schema's `CHECK`, checked again by the opener), so the key is one opaque basename: no client filename, display name or request text ever builds a path, and no `..`, separator or absolute path can occur. A row with a hostile id cannot be inserted.
- **Opening and streaming (`assets.open_asset_file`):** the root is opened as a directory with `O_NOFOLLOW`, the file is opened relative to that descriptor with `O_NOFOLLOW`, `O_NONBLOCK` and `O_CLOEXEC`, and `fstat` on the opened descriptor must say regular file. The size and the bytes come from that descriptor, so the path is never opened a second time (a name replaced or unlinked after the check changes nothing), and a named pipe cannot hold the request. `Path.resolve` is not used. A platform that cannot open relative to a directory descriptor fails closed. Descriptor ownership: the opener closes every descriptor it opened if it fails; the route closes the file if recording fails; from the return the flow owns it, closes it if the count check or the commit fails, and the response closes it in a `finally` around the whole ASGI call.
- **Storage failures are integrity failures:** a row whose file is missing, unreadable, a symlink, a directory or a pipe is not an ordinary download. It rolls back, records no `asset.read`, answers the generic 500 (which names no path and no id) and is logged. Nothing in the quarantine directory is reachable from this route even if a row exists for it. Nothing verifies the content against a hash: that is for the lifecycle milestones, and no immutability is claimed.
- **Local storage assumptions:** the root is on a local filesystem that untrusted users cannot write to. Its parent directories are followed like any configured path (a symlinked parent, such as `/var` on macOS, is the administrator's choice); only its last component and everything below it are opened without following. A hard link planted by someone who can already write into the root is invisible to a no-follow open. A network filesystem is not supported.
- **Tests (M1G-B):** `tests/test_asset_files.py` (38) for the opener, `tests/test_asset_access_api.py` (72) for the HTTP behaviour, `tests/test_app.py` for the new dependency and route, and the shared harness (`tests/support/http_lab.py`) now seeds an asset root, three synthetic assets and a caller engaged in both productions, and holds the scripted ASGI client. The API tests cover cross-production isolation (including that caller), 404 identity, invalid ids, revocation and expiry with the same token, fabricated claims, quarantined and missing bytes, symlink, directory, pipe and symlinked-root attempts, hostile display names, the order of the work, failures before the commit and after it (a send failing on the start or mid-stream, a disconnect before the first byte, cancellation, normal completion) and concurrency in both orders. A scratch run removed one safeguard at a time (19 variants for the opener, the route and the wiring) and the tests failed every time.
- **Limits:**
  - `asset.read / allowed` is a statement about authorisation and the server's commitment to serve, not about delivery. There is no completion event, and a transport failure after the commit is only logged by the server.
  - A response already authorised is not cut off when authorisation is withdrawn. The file stays open while a slow client reads, so many slow clients can hold many descriptors and worker threads (not the writer lock). There is no size limit and no rate limit in M1G.
  - Every request that reaches the handler appends one audit row, including every miss (AM-20).
  - An asset id containing a newline matches no route and is the framework's 404, unaudited (AM-18).
  - The bytes are trusted because they are in the trusted root. Anything that can write there can change what is served.

**AM-22: M1H initiation and ingest (2026-11-04).** Implemented on the security reviewer's instruction after M1G-B was committed (`e2a4f31`), as one slice. After a final source-level review it was corrected (no-clobber placement, cleanup limited to the file the request placed, reconciliation that reports instead of deleting, the maintenance-window restriction) and committed locally as one commit (gate G3 covers M1H to M1K, AM-6). It is the F-05 reference and the first writer of client bytes. Synthetic content only. Sealing, the checks of declared against actual, the scanner, acceptance and promotion (M1I to M1K) do not start with it.
- **The M0 contract implemented**, in the words of the design: the vendor sends JSON with a display filename, a declared size, a declared SHA-256 and a media type (M0 §2 step 3), then streams raw bytes with a `PUT` into quarantine under a size cap enforced while streaming (step 4); the roots are separate and the keys are server-generated (§4); the display name is metadata, validated, and never builds a path (F-05); declared values are for consistency checks and display, never content identity, cache keys, storage paths or verdicts (Addendum §5.1); the lifecycle is the Addendum §5.2 diagram, of which M1H performs `INITIATED` and `INITIATED -> UPLOADED`; authorisation is checked when a request starts and a started transfer may finish (§5.7); no `python-multipart` (a raw body).
- **The lifecycle belongs to deliveries.** A new `deliveries` table holds the state (`store.DeliveryState`, the ten states of §5.2 in its order, as a `CHECK`). Triggers make a delivery start as `INITIATED`; never be deleted or replaced (an `INSERT OR REPLACE` that collides on id, rowid or storage key is refused, as for engagements); keep its identity and ownership fixed (id, production, owner, storage key, display name and all three declared values, creation time, rowid); change state only along the twelve arrows of §5.2 (`store.DELIVERY_TRANSITIONS`; `PROMOTING -> PROMOTING` is not a change of state); and write the receipt (`received_size`, `received_sha256`, `uploaded_at`) once, together with the move out of `INITIATED`. `assets` has no state and gains none. All hundred ordered pairs of states are tested against the design copied into `tests/test_delivery_store.py`.
- **Roles and ownership.** Only a `vendor` may declare or upload (`initiate_delivery` and `upload_delivery`; M0 names the vendor for both steps); a coordinator is a 403 `role_not_permitted`. The production always comes from the URL. A delivery is owned by the verified subject that declared it, in that production, for good. M0 does not say whether another vendor of the same production may upload to it; this slice says no (assumption A-2 below): the lookup `ingest.get_delivery_in_scope` is one parameterised `SELECT` binding the delivery id, its real production, the requested production, the owner's verified `(issuer, subject)` and the owner's current unrevoked engagement, as for assets (AM-21). A missing, other-production, other-owner or malformed delivery id is one generic 404 (`{"detail":"Not found"}`, recorded `access.denied` as `not_found_or_forbidden` or `invalid_identifier`); production-level failures stay the flow's generic 401 and 403.
- **Declaration** (`POST /productions/{production_id}/deliveries` -> 201 `{delivery_id, state: "INITIATED"}`). Exactly the members `display_name`, `declared_size`, `declared_sha256`, `declared_media_type`; any other member (a production, owner, state or storage key) is a 400 naming only `body`. `display_name`: 1 to 200 characters, none a control, format (bidirectional), surrogate or separator character, no `/` or `\`, not `.` or `..`; stored exactly. `declared_size`: an integer (not a bool) from 0 to the application's upload limit. `declared_sha256`: 64 lowercase hexadecimal characters. `declared_media_type`: `type/subtype` tokens with no parameters, at most 255 characters (the schema's bound). A 400 names only the member (`field`); a body over 4 KiB is a 413, judged after authentication and authorisation. The id and the storage key are generated by the server (`store.add_delivery`), independently of each other and of every input; the storage key is never returned. No file is created.
- **Upload** (`PUT /productions/{production_id}/deliveries/{delivery_id}/content` -> 201 `{delivery_id, state: "UPLOADED", received_size, received_sha256}`), in two short transactions with the bytes between them, so the SQLite writer lock is never held while a client sends:
  1. `request_flow.decide`: `BEGIN IMMEDIATE`, authenticate (ES256 verifier), authorise `upload_delivery` for the URL's production, look the delivery up in scope, require `INITIATED` (else 409 `{"detail":"Delivery is not awaiting content"}`, recorded `delivery.request_rejected / state_conflict`), refuse an honest `Content-Length` over the limit (413) without reading, record `delivery.upload_started`, `COMMIT`. **No byte of the body has been requested before this commits.** Only the very `Decision` the committed operation returned admits the upload, so a failure after the operation (the audit count, the commit) reads nothing.
  2. The body is read with `request.stream()`, one chunk at a time (the whole body is never gathered and `Request.body/json/form` are never called), and each chunk goes to `quarantine.IncomingFile`: counted against `max_upload_bytes` on the bytes that actually arrive (`Content-Length` is only an early hint, absent, wrong or not a number), hashed with SHA-256 as it is written, and written to a staged file under `quarantine/.incoming/` named by 32 random hex characters, opened `O_CREAT|O_EXCL|O_NOFOLLOW`, mode 0600. The chunk that would cross the limit is not written and reading stops there. A client that goes away, or a request that is cancelled, has its staged bytes removed.
  3. `request_flow.proceed`: `BEGIN IMMEDIATE`, one clock read of its own, compare-and-set `INITIATED -> UPLOADED` naming the delivery, its production, its owner and the state, then `quarantine.publish` (a no-clobber placement at the delivery's storage key, below), then record `delivery.uploaded`, then `COMMIT`. It authenticates and authorises nobody (M0 §5.7); `proceed` takes the caller and the `AuthorizedEngagement` that `decide` produced for this request, and a guard fails if anything but `ingest.py` refers to it.
- **Digest.** `received_sha256` is the SHA-256 of the bytes this request actually wrote, computed as they were written. It is **not H**: H is the digest of the stored bytes at seal (Addendum §5.1), which M1I computes by reading quarantine again, because quarantine is mutable storage. The declared hash, size and type are recorded and compared with nothing here: a mismatch is a decision for the seal (§5.2 row 1: `SEALING -> REJECTED`), and `INITIATED -> REJECTED` is not an arrow, so an upload with a mismatching declaration is accepted as `UPLOADED` by design.
- **SQLite and the filesystem are not one atomic transaction, and nothing here says they are.** The placement comes after the compare-and-set and before the commit. A crash, or a failed audit insert or commit, can therefore leave a file that no committed row claims (never served, never read), but never a committed `UPLOADED` row whose file was not placed.
- **Placement never replaces (`quarantine.publish`).** The staged file is hard-linked to the storage key relative to the two directory descriptors (`os.link`, `follow_symlinks=False`), which the kernel refuses with `FileExistsError` when anything occupies the key (a regular file, a directory, a pipe, a symlink, even a dangling one); only then is the staged name unlinked. The staging directory is inside the root, so source and destination are on one filesystem; another mount or a filesystem without hard links fails closed. Verified on the supported macOS environment (`os.link` supports `dir_fd` and `follow_symlinks=False`; existing file and dangling symlink both refused, nothing replaced). A collision is a generic 500 with the delivery still `INITIATED`, no `delivery.uploaded`, this request's staged file removed and the occupant exactly as it was (same inode, same content or target), and it is logged with the `FileExistsError`.
- **Cleanup takes back only what this request placed.** `quarantine.Received` carries the device and inode of the file that was written (`fstat` on the descriptor). After a completion that failed (status 500 or above), `_take_back_what_this_request_placed` runs under `BEGIN IMMEDIATE`: if the delivery is no longer `INITIATED` (an error came after a commit that did happen) nothing is touched; otherwise `quarantine.remove_if_same_file` unlinks the entry at the key only if it is a regular file with that device and inode. A file that was already there when the placement was refused, one that has replaced ours since, a symlink (even to our inode), or nothing, is left exactly as it is. `remove_if_same_file` is the only deletion of a file at a storage key in the code base (`tests/guards/test_delivery_scope.py`), and there is no unconditional remove. If the cleanup cannot run (the database is locked, the request is cancelled before it), the leftover is this request's but nothing can prove it any longer, so it stays; it makes a retry of that delivery fail closed (a 500) until a person has looked at it and removed it.
- **`reconcile` reports ambiguity and deletes nothing at a storage key.** A regular file at the key of a delivery that is still `INITIATED` cannot be told from one that someone placed there (nothing recorded says whose it is, and no schema change was made to record it), so `ingest.reconcile` returns it as `ambiguous` for manual handling. One whose delivery is `UPLOADED` or later is the delivery's bytes; one that no delivery claims (`unreferenced`) and anything that is not the server's (`foreign`) are reported and left alone, so a mistaken root cannot cost anyone else's files; a delivery past `INITIATED` whose file is not a regular file is `missing`, never repaired. The state is read under the writer lock, so a completion that is committing at that moment is seen as `UPLOADED` and not reported. The only thing it removes is a staged file in `.incoming` at least `min_age` old.
- **`reconcile` is a manual maintenance-window operation (C2).** No uploads may be active when it runs. `min_age` is an age threshold on the staged file's last write, not proof that its upload is inactive. Running it during an active upload can interrupt that upload: its staged file is removed from under it and the upload fails with a generic 500, the delivery still `INITIATED`, never a false `UPLOADED` (`tests/test_quarantine_reconcile.py::test_reconcile_while_an_upload_is_arriving_can_interrupt_it_so_it_is_a_maintenance_window_operation` records the observed interaction; it does not claim that the implementation prevents it). It must not be scheduled or called automatically under the current contract, and **M1M must establish an active-upload exclusion mechanism before any automated reconciliation.** No `flock`, scheduler or background service exists in M1H.
- **Concurrent uploads.** M0 has no state between `INITIATED` and `UPLOADED`, so none is invented: two uploads to one delivery can both be admitted and both stream; the compare-and-set lets one win and the other gets a 409 (recorded `delivery.upload_failed / state_conflict`) with its staged bytes removed; the loser never places a file, so it cannot change the winner's bytes.
- **Failures.** Before the second transaction commits, every failure leaves the state `INITIATED` and nothing staged. A full disk, a refused placement or a failed commit is the flow's generic 500 (no path, no errno in the answer), logged, with no completion event: `delivery.upload_started` stands and the delivery still awaits content. A cancelled request records no completion event for the same reason. A body over the limit is a 413 with `delivery.upload_failed / payload_too_large`; a client that goes away is `delivery.upload_failed / upload_interrupted` (outcome `recorded`).
- **Audit vocabulary** (a reviewed change; `tests/test_audit.py`): actions `delivery.initiated`, `delivery.request_rejected`, `delivery.upload_started`, `delivery.uploaded`, `delivery.upload_failed`; reasons `state_conflict` and `upload_interrupted`; object type `delivery`. One event for each committed transaction. No filename, size, digest, path or body is recorded. `delivery.upload_started` records the committed admission to begin receiving an upload; it does not guarantee that any byte arrived or that the upload completed, and a start with no later event means in progress, a server fault, a cancelled request or a crash. `delivery.uploaded` is written in the same transaction as the move to `UPLOADED` and the placement, so it exists only when that transition committed, and no event claims a successful upload when the placement fails.
- **Configuration.** `Dependencies` gains `quarantine_root` (absolute `Path`) and `max_upload_bytes` (an `int`, not a bool, from 1 to 2**63 - 1). The two roots must be separate: neither may be, contain or lead to the other (compared after resolving symlinks, at construction). There is no default for the limit: it is a deployment choice for the runner (M1M); the test harness uses 64 KiB. `app.py` hands the trusted root only to the asset route and the quarantine root only to the ingest routes; `quarantine.py` and `assets.py` are the only modules that open, move or delete files and neither names the other's root (`tests/guards/test_delivery_scope.py`).
- **The request flow** (`request_flow.py`) changed only as far as an upload needs: `handle` is now `respond(decide(...))`; `_run` takes the decision as a function so that `proceed` can reuse the one order (one `BEGIN IMMEDIATE`, one clock read, exactly one audit event, `COMMIT`, generic error on failure); `_failed` became the public `failure`. Every existing endpoint is unchanged and its tests pass untouched.

- **O-1 is resolved (reviewer, 2026-11-04): Option A.** One authoritative digest H, computed from the actual quarantined bytes by `trust.content_identity(delivery, stored_file)` and by nothing else. The same H is: compared with the vendor's declared SHA-256; the verdict-cache key; the digest a verdict is bound to; the sealed digest recorded on the delivery; and what acceptance and promotion will compare against. - **Not implemented here:** the internal arrows `SCAN_FAILED → SEALING`, `SCAN_PASSED → SEALING` and `SEALING → INTEGRITY_FAILED` (a rescan, a stale verdict, a re-hash that differs from H). A vendor cannot retry a failed scan: a second seal of anything not `UPLOADED` is a 409.
- **Endpoint and roles.** `POST /productions/{production_id}/deliveries/{delivery_id}/seal`, no body. Authz action `seal_delivery` is the vendor's alone (M0 §2 step 5), and only the delivery's owner can seal it: another vendor of the same production, another production's vendor and a missing or malformed id are the generic 404 (AM-22); a coordinator is a 403 `role_not_permitted`. Answers: 200 `SCAN_PASSED` (`delivery_id`, `state`, `sealed_size`, `sealed_sha256`, `engine {id, version, kind}`, `verdict_valid_until`); 422 `REJECTED` with `reason` `checksum_mismatch`, `unsupported_type` or `detection` (and `engine` only for a detection, the one verdict-bearing rejection); 502 `SCAN_FAILED` with `reason` `unavailable`, `timeout` or `bad_response`; 409 `{"detail": "Delivery is not ready to be sealed"}` for any state but `UPLOADED`; 500 generic for a file that cannot be inspected or any fault. The response does not say whether a verdict was reused.
- **Two short transactions with the inspection between them** (the same shape as the upload): (1) `request_flow.decide`: authenticate, authorise, scoped lookup, require `UPLOADED`, compare-and-set `UPLOADED → SEALING` naming the delivery, production, owner and state, `delivery.seal_started`, commit. Two concurrent seals cannot both pass this: the second sees `SEALING`. (2) The inspection, outside any transaction, so the writer lock is never held while a file is read, hashed or scanned. (3) `request_flow.proceed`: the verdict row if the scanner made one, compare-and-set `SEALING →` outcome with the seal, one audit event, commit. The verdict-cache read in (2) is a plain read on its own connection, taken at the instant the cache is consulted; a verdict can therefore expire between that read and (3), which leaves a `SCAN_PASSED` whose verdict is already stale, a state M0 row 8 already provides for and acceptance refuses (M1J).
- **Validation order (M0 §5.2), checked by a recorded call sequence:** H is computed once (the digest is needed in every record, so the hashing pass is made even when the size already differs); the measured size against the declared size; H against the declared SHA-256 (either differing is `REJECTED(checksum_mismatch)` with no cache lookup and no scanner call); the file signature; the cache; the scanner on a miss. The declared hash is referenced once in `trust.py`, in that comparison.
- **The seam.** `content_identity(delivery, stored_file)` is a module-level function the gate looks up when it is called, so a lab (M2D) replaces exactly that one function in a test harness; the reference hashes the file and never reads `delivery`. Its result is a `ContentIdentity`, the only thing `lookup_verdict` accepts as a key, so a bare declared string raises `TypeError` there. The controlled F-03 feasibility run (scratch harness, not in the repository; its vulnerable function exists only in that scratch file) shows the reference implementation rejecting a marker file that declares the hash of a previously scanned file before any cache or scanner call, and, with only `content_identity` replaced, a cache hit that never calls the scanner and ends at `SCAN_PASSED`. It stops there, as M0 §3 R1 requires; promotion's re-hash (F-04) is not bypassed and not yet built.
- **What H binds, and what it does not.** H and the measured size describe the bytes read through one descriptor of the file at the delivery's opaque storage key: opened without following a symlink, a regular file only, relative to the validated root, every read a `pread` at an explicit offset (`quarantine.open_stored`). It binds content, not a path, name, inode or modification time: a cached verdict applies to H. A digest does not make mutable storage immutable. `ensure_unchanged` compares device, inode, size, mtime and ctime of the descriptor with their values at open and checks that the name still leads to the same file; it runs at the end of the hashing pass, and before a verdict is recorded. It detects a change made while the file was being inspected; it does not prevent one, and bytes can change after the seal. The promotion re-hash (F-04) stays necessary and is unchanged.
- **The scanner contract (`scanner.py`).** `Scanner` has an `engine` (`EngineIdentity`: id, version, kind, policy fingerprint) and `scan(stream, *, timeout_seconds) -> ScanResult(verdict, scanned_sha256)`. The scanner is given the stream and nothing else, so it cannot copy a digest; the gate hands it the stored file's own stream from offset 0 and accepts the reply only if it is a well-formed `ScanResult` whose `scanned_sha256` equals H. A malformed reply or a digest that is not H is `SCAN_FAILED(bad_response)`, even with a `no_detection` verdict and even for a `detection`. The shipped `LabSyntheticMarkerScanner` reads to the end in blocks, hashes what it read, and finds one lab marker string across block boundaries; its policy fingerprint is the SHA-256 of its name, version and marker. `Dependencies.scanner` has no default; `create_app` refuses an object without a scan method and an `EngineIdentity`.
- **Signature allowlist (a lab assumption, A-B1 below).** PNG, JPEG, ISO base media (QuickTime and MP4: `ftyp` at offset 4), WAV (`RIFF` and `WAVE`), OpenEXR and Matroska. An archive, text, an empty file and a truncated signature are `REJECTED(unsupported_type)`. The declared media type is display metadata and is neither compared with the signature nor relied on.
- **Schema (the one initial schema; `SCHEMA_VERSION` stays 1, as in AM-22 A-1).** `deliveries` gains `sealed_size`, `sealed_sha256`, `receipt_matched`, `state_reason` and `verdict_id`. The database refuses: a seal before `SEALING`, or a state after `SEALING` without one; half a seal; a reason that does not belong to the state (`REJECTED`: `checksum_mismatch`, `unsupported_type`, `detection`; `SCAN_FAILED`: `unavailable`, `timeout`, `bad_response`; none elsewhere); a change to a seal once written (`deliveries_seal_is_final`); and `SCAN_PASSED` without a `no_detection` verdict bound to the delivery's own sealed digest (`deliveries_pass_needs_a_matching_verdict`, so no code path can write a passing scan without its verdict). The new `verdicts` table holds H, engine id, version, kind, policy fingerprint, verdict, the scanner's reported digest (which the schema requires to equal H), scan time, `valid_until` and the origin delivery; rows are never changed, deleted or replaced. The lifecycle states and the twelve arrows are unchanged.
- **The cache.** A verdict is reused only if its digest, engine id, version, kind and policy fingerprint equal the current ones exactly, its verdict is `no_detection`, and `valid_until > now` (so not at the instant it expires). The newest such row wins. A detection is recorded (the delivery points at it) and never reused; a failed scan, a malformed reply and a digest mismatch make no row, so they are never cached. Old rows are kept for audit and never applied. The engine kind is part of the key (stricter than M0's list). Reuse is across productions, as M0 specifies, which means a vendor who seals bytes that another production already delivered avoids a scan; the response does not say so, but timing might (a limit, below).
- **Audit (one event per committed transaction).** Actions `delivery.seal_started` (allowed), `delivery.scan_passed` and `delivery.verdict_reused` (recorded), `delivery.rejected` (denied; reasons `checksum_mismatch`, `unsupported_type`, `detection`) and `delivery.scan_failed` (recorded; reasons `scanner_unavailable`, `scanner_timeout`, `scanner_bad_response`). The start event records committed admission to inspect; it does not say the inspection finished. A fault (a missing, unreadable or changed file; an unexpected scanner exception; a failed commit) is a generic 500 with no outcome event: the delivery stays `SEALING`. **A-B5 is closed.** M0 §5.3 says `engine.kind` appears in every verdict-bearing audit event, so `audit_events` has one constrained column, `engine_kind TEXT CHECK (engine_kind IN ('synthetic'))`, and `audit.record_event(..., engine_kind=None)` takes a member of the closed `audit.EngineKind` vocabulary (the same single kind the scanner contract and the verdicts table permit), never free text. `record_event` requires it on the events about a scanner verdict (`delivery.scan_passed`, `delivery.verdict_reused`, `delivery.rejected` with reason `detection`) and on `delivery.scan_failed`, which has no verdict row and invents no verdict id but records the configured scanner's kind; it refuses a value on every other event, so the column is NULL on all engagement, asset, upload, seal-start, checksum and signature events. The table stays append-only (the existing triggers cover the new column), the schema fingerprint check covers it, and the one-event-per-transaction count is unchanged. Nothing about `content_identity`, the checksum comparison, the cache key or the F-03 behaviour changed.
- **Failure handling.** A seal whose first transaction does not commit reads no file. A scanner failure of the three kinds is recorded as `SCAN_FAILED` with no verdict. Any other failure leaves `SEALING`, which accepts nothing, is not retried by the vendor and awaits an internal rescan (not implemented). A commit, an audit insert or a verdict insert that fails in the second transaction rolls back all of it: the verdict row goes with the state, and the database would refuse a `SCAN_PASSED` without it anyway.

**AM-24: M1J coordinator inspection, hash-bound acceptance and the internal rescan (2026-11-04).** Implemented on the security reviewer's instruction after M1I was committed (`eaea1fb`, with the engine-kind audit correction that closed A-B5). The reviewer accepted it on 2026-11-04 and it is committed locally as one commit. Synthetic content only. Promotion (M1K) and everything after it do not start with it. The M0 sources are Addendum §2 steps 6 and 7, §5.1 (H is what acceptance binds to), §5.2 (the two arrows `SCAN_PASSED → ACCEPTED` and, as *internal* arrows, `SCAN_FAILED → SEALING`, `SCAN_PASSED → SEALING` and `SEALING → INTEGRITY_FAILED`; outcome row 8), the §6 milestone table (M1J: acceptance, hash-bound, coordinator only, stale verdict refused; gate A9) and the A9 decision (revocation blocks acceptance; natural expiry does not). The lifecycle states and the twelve arrows are unchanged. The M0 table assigns acceptance to M1J and does not say which milestone owns the internal rescan; AM-23 left it for the milestone that decides how a system actor appears in the audit trail and what makes a verdict stale, which is this one, so the smallest rescan is here (A-J6).
- **Inspection.** `GET /productions/{production_id}/deliveries/{delivery_id}/seal` (the same resource as the vendor's seal, a different method), authz action `inspect_delivery`, a coordinator's alone. The delivery is found by one scoped statement (`acceptance.get_delivery_for_review`) that binds the delivery id, the URL's production, the caller's verified issuer and subject and a *current, unrevoked coordinator engagement* in that production, so a delivery id alone reaches nothing. A missing, other-production or malformed delivery is the one generic 404 (`access.denied`, `not_found_or_forbidden` or `invalid_identifier`); a vendor (the owner included) is a 403 `role_not_permitted`; a coordinator of another production is the flow's 403 through the delivery's URL and a 404 through their own. The 200 shows `delivery_id`, `state`, and where they exist: `reason` (a rejection or a failed scan), `sealed_size` and `sealed_sha256` (H), and for the attached verdict `verdict`, `engine {id, version, kind}`, `policy_fingerprint`, `verdict_scanned_at`, `verdict_valid_until` and `verdict_in_force` (a no_detection verdict for H by the engine the server runs now that has not expired at this instant), then `accepted_sha256` and `accepted_at` once accepted. It reads no file, calls no scanner and changes nothing; it records `delivery.viewed` (allowed), with the verdict's engine kind when a verdict is shown.
- **Acceptance.** `POST /productions/{production_id}/deliveries/{delivery_id}/accept` with the body `{"sealed_sha256": "<64 lowercase hex>"}` and nothing else (at most 4 KiB, exact member set, no repeated member), authz action `accept_delivery`, a coordinator's alone. The delivery is found first, by the same scoped statement; only then is the body judged, so a body error cannot tell a caller what exists. In one transaction, on the one instant that transaction read from the clock, the checks run in this order and nothing changes unless all hold: (1) state is `SCAN_PASSED` (else 409 `state_conflict`); (2) the digest named equals the delivery's immutable sealed digest H (409 `digest_mismatch`; the named digest is compared with H and is never stored, keyed or used as an identity); (3) the delivery's owner's engagement in that production has not been revoked (409 `engagement_revoked`; A9); (4) the attached verdict is a `no_detection` verdict for H whose scanner-reported digest is H (409 `verdict_not_applicable`), by exactly the engine id, version, kind and policy fingerprint the server runs now, with `valid_until` strictly later than the transaction's instant (409 `verdict_stale`). Then one compare-and-set `SCAN_PASSED → ACCEPTED` that names the delivery, its production, the sealed digest and the verdict that were checked, writing the digest, the instant and the coordinator, and `delivery.accepted` (allowed), in the same transaction. 200 shows `delivery_id`, `state`, `accepted_sha256`, `accepted_at`, `engine` and `verdict_valid_until`. The 409 body is `{"detail": "Delivery cannot be accepted", "reason": <code>}`: the coordinator is authorised to see the delivery, so the code is shown to them. A malformed body is 400 `{"detail": "Invalid request", "field": ...}` and an oversized one 413, both after authorisation, as at declaration. Every refusal is `delivery.acceptance_refused` (denied) with the reason; the two verdict reasons carry the verdict's engine kind.
- **Why the verdict is checked again here.** `SCAN_PASSED` says a verdict was good when the seal committed, and the verdict cache is read outside the sealing transaction (A-B4), so a delivery can already be stale when it is written. Staleness is therefore decided at acceptance, from the verdict row and the clock read of the accepting transaction, and nothing about it is stored. `valid_until` is the first instant at which a verdict no longer counts (`valid_until <= now` is stale), the same boundary as the cache. A scanner upgraded since the seal makes its old verdicts stale (exact equality, never "newer than"): they are kept and not applied, and the delivery waits for a rescan. Acceptance reads no file (Addendum §5.4: "after scan, before accept" is caught at promotion), so a change to the stored bytes is not noticed here. Verdict validity is not rechecked at promotion, which the Addendum records as a gap.
- **Concurrency and atomicity.** The request is one `BEGIN IMMEDIATE` transaction in the shared flow: authenticate, authorise (the coordinator's current engagement, on the same instant), look up, check, change, record, count exactly one audit event, commit. Two concurrent acceptances serialise on the writer lock: the second finds `ACCEPTED` and is refused (`state_conflict`); a failed audit insert or commit rolls the acceptance back and the answer is the generic 500. The compare-and-set must change exactly one row; anything else is a fault, not a refusal.
- **Schema (the one initial schema; `SCHEMA_VERSION` stays 1).** `deliveries` gains `accepted_sha256`, `accepted_at` and `accepted_by` (a subject). The database refuses: half an acceptance record; one in a state before `ACCEPTED`; one whose digest is not the sealed digest; `ACCEPTED`, `PROMOTING` or `PROMOTED` without it or without a verdict; entry into `ACCEPTED` unless the delivery's verdict is a `no_detection` verdict for its own sealed digest (`deliveries_acceptance_needs_a_matching_verdict`); and any change to the record or to the verdict once accepted (`deliveries_acceptance_is_final`). `INTEGRITY_FAILED` may or may not carry a record: it follows `PROMOTING` (accepted) or `SEALING` (a rescan; never accepted).
- **The internal rescan (`trust.rescan`).** A function for the operator's own code, like the ingest reconciliation: there is no route and no request can start one. `rescan(delivery_id, *, clock, database_path, quarantine_root, scanner)` takes the delivery's id and nothing that could name a digest. Eligible: `SCAN_FAILED`, and `SCAN_PASSED` only while its verdict has any `verdict_problem` (expired, or another engine, version, kind or policy than `scanner`'s); a verdict that still counts is not rescanned, and no other state is. It does what a seal does, from the sealed values, in two short transactions with the inspection between them: (1) compare-and-set to `SEALING` (clearing the reason and the verdict link, keeping the seal), `delivery.rescan_started`; (2) the stored bytes are hashed by the same `content_identity()` seam and compared with the sealed H and size *first*: any difference is `INTEGRITY_FAILED` (final, `delivery.integrity_failed` with reason `sealed_content_changed`, H not replaced, no cache, signature or scan); equal bytes go through the signature check, the cache and the scanner exactly as at a seal and end in `SCAN_PASSED`, `SCAN_FAILED` or `REJECTED`. A new verdict is a new row; the old one is kept and never applied. A refused rescan (`RescanRefused`: unknown or malformed id, an ineligible state) is itself recorded (`delivery.request_rejected`).
- **The system actor.** A rescan is neither a vendor's nor a coordinator's act, so it is recorded under one named identity, `audit.SYSTEM_RESCAN` = issuer `system:content-boundary-lab`, subject `rescan`, in a namespace (`system:`, compared without regard to case) that no verified token can carry: `TrustedSettings` refuses a trusted issuer in it (so a token naming it cannot authenticate), and `audit.record_event` refuses it to everyone but the named system actors, each only for its own events (the rescan's: `rescan_started`, `scan_passed`, `verdict_reused`, `rejected`, `scan_failed`, `integrity_failed`, and `request_rejected`). It cannot accept, view or read an asset. It is an audit convention and a bound on what may be recorded under it, not a credential: nothing authenticates as it, and the code that calls `rescan` is trusted configuration, like the rest of the operator's tools. `request_flow.run_system` runs one transaction under it with the flow's own rules (BEGIN IMMEDIATE, one clock read, exactly one audit event, commit) and raises on failure to the operator's code instead of answering a client; only `rescan` calls it (a guard).

AND d.production_id = ?`), so a delivery of another production is the same refusal as one that does not exist (`PromotionRefused`, recorded `not_found_or_forbidden`); nothing a client sent (a URL, a checksum, a filename) is an input. `promotion.reconcile(...)` is the recovery pass. - **Protocol (M0 P1 to P4, with the order the reviewer asked for inside P4).** P1 `begin`: `request_flow.run_system`, one `BEGIN IMMEDIATE`: read the delivery in the production, require `ACCEPTED`, require the accepted digest to equal the sealed digest and the attached verdict to be a `no_detection` verdict for it (`trust.verdict_binding_problem`), then one compare-and-set `ACCEPTED → PROMOTING` naming the delivery, production, accepted digest and verdict, which records a fresh attempt id and the server-generated key the asset will have; `delivery.promotion_started`; commit. P2 `stage`, outside any transaction: open the quarantined source with `quarantine.open_stored` (no symlink followed, a regular file only), create `trusted/.staging/<attempt>` with O_EXCL and mode 0600 and `copy_verified` into it. P3 and P4 `publish`, in one short `BEGIN IMMEDIATE`: recheck that the delivery is still `PROMOTING` for this attempt and key, insert the asset row, check that the staged file is the very file that was verified (device, inode, size), link it to `trusted/<asset key>` (no clobber), compare-and-set `PROMOTING → PROMOTED`, `delivery.promoted`, commit; only then is the staged name dropped. `fail` is the other branch of P4: the compare-and-set `PROMOTING → INTEGRITY_FAILED` and `delivery.integrity_failed` (reason `sealed_content_changed`). The writer lock is never held while a file is read or copied.
- **The check that matters (the F-04 seam).** `copy_verified(source, target, promoting)` is the one function that copies and verifies. The staged file (`assets.StagingFile`) counts and hashes the bytes it is handed as it writes them, `finish()` checks that count against the size of the file on disk, and the result is compared with the immutable accepted digest and size inside `copy_verified`: nothing from `content_identity`, the seal's fields or the database stands in for it (a test replaces `content_identity` and `lookup_verdict` with functions that fail if called, and a guard fails if `promotion.py` names `content_identity`). A different byte, a different length, a cut-short copy, or more bytes than were accepted (the staged file refuses the chunk that would cross the accepted size) is `ContentChanged`; the staged file is removed before the failure is recorded; the delivery goes to `INTEGRITY_FAILED` with the accepted digest unchanged and nothing rebound to what was found. A source that changes while it is read is judged by the bytes that were written, so only bytes with the accepted digest can pass. A source that is missing, a symlink (O_NOFOLLOW), a directory or a pipe is also `INTEGRITY_FAILED` (assumption A-K3); any other failure (a full disk, a read error, an interrupted copy) removes the staged file, publishes nothing, leaves the delivery `PROMOTING` and raises, and `reconcile` runs the attempt again with the same key.
- **Publication, and what the database does and does not say.** Final names are the asset's own server-generated id (the existing asset route is unchanged and serves `trusted/<id>` only while an `assets` row exists, so a file under a `PROMOTING` delivery is not served; M0 §5.4's "window" is closed by the database being authoritative). The link is a hard link relative to directory descriptors, which the kernel refuses when anything at all occupies the key; the directory is synced after it (V8, below). The asset row, the move to `PROMOTED` and the audit event commit together or not at all. If anything after the link fails (the audit insert, the commit, a recheck), the exact file this promotion linked, recognised by device and inode with the writer lock held and the delivery still `PROMOTING`, is removed, and no other file: a file that was already there, one that replaced ours, or nothing, is left as it is. This is not an atomic pair of a database commit and a file operation and is not presented as one. If cleanup itself fails, the leftover is logged and `reconcile` reports it.
- **Schema (the one initial schema; `SCHEMA_VERSION` stays 1).** `deliveries` gains `promotion_attempt` and `asset_id` (32 hexadecimal characters each, unique, together, only from `PROMOTING` on, required in `PROMOTING` and `PROMOTED`, written once: `deliveries_promotion_is_final`). `assets` gains `delivery_id` (unique), `sha256` and `size`, all or none: a seeded asset has none. - **Idempotency and concurrency.** Promoting a `PROMOTED` delivery returns the original result from a read, with no transaction, event or change. Two callers: only the compare-and-set winner leaves `ACCEPTED`; a loser is refused (`state_conflict`) whether it arrives during the winner's copy (which holds no lock) or after, and the no-clobber link is a second barrier. A caller that read `ACCEPTED` just before the winner finished is refused too, rather than handed the result: the contract's idempotency is for a delivery that is already `PROMOTED` when the call begins.
- **Recovery (`promotion.reconcile`, M0's crash table, one row each).** For each `PROMOTING` delivery: nothing on disk, a partial staged file, or a complete one not linked: remove the staged name (the attempt's own) and run the attempt again from the copy, with the same key; the staged file and the key are one file (linked, not yet unlinked; exactly two names): adopt it if it passes the checks below and finish; only a key with one name (linked and unlinked, not committed): adopt it on the same checks. **Adoption** (`_recover`) needs all of these: the accepted digest and size come from the delivery's immutable acceptance and seal records (read by `_rebuild`, written once by triggers); the file is opened under the trusted root with no symlink followed (`assets.measure`: root and file opened with `O_NOFOLLOW`, relative to a descriptor) and must be a regular file; every byte is read and hashed and counted, and the digest and size must equal the accepted ones; the link count is the one the case implies; and the file's fingerprint (device, inode, size, link count, modification and status-change times, `assets.Entry`) must be identical at the first look, before the read, after the read (and the name must still lead to that inode), and in the writer-locked transaction that writes the asset row, immediately before the compare-and-set (`_finish`, `link=False`). Any difference rolls the transaction back before an asset row exists and the file is reported. The check and the commit are not one atomic act and no filesystem primitive makes them one; what remains is the interval between that final check and the commit inside one transaction, which needs write access to the trusted root, which M0 §5.4 assumes is controlled outside the application (the same exposure as "after promotion: not prevented"). Everything else is `ambiguous` and left exactly as found, never adopted, overwritten, moved or deleted: a key that is not a regular file, one with another name elsewhere, a staged file and a key that are different files, bytes that are not the accepted ones (including a file that is very probably this attempt's own and has changed since it was verified), a file that changed or was replaced during the verification, and a staged name that is not a plain file. M0 §5.4 for the case "P3, before P4 | `PROMOTING` and target": "Re-hash target. If equal to H, run P4 success. Otherwise move it out of `trusted/` and run P4 failure." The first sentence is implemented, with the identity checks above added; the second is not: there is no investigation area in M0, moving a file is a change to something that cannot be proved ours, and the reviewer's rule is to preserve it (assumption A-K2). No security invariant depends on the move: no asset row is written for it (the asset route serves a file only while a row exists), nothing is overwritten, and `promote` refuses a `PROMOTING` delivery, so it cannot be promoted again; what the move would have added is removing the file from the directory for a consumer that reads `trusted/` without the database, which M0's "Window" paragraph already requires not to be done. The delivery stays `PROMOTING` until a person decides. Then the staging directory: the leftover plain-file name of a failed attempt, or of a finished one when it is the published file, is removed; any other name is reported as `unreferenced`. Running it twice gives the same state.

## 4. Technical constraints

Details are in the addendum sections cited. Where this summary and the addendum differ, the addendum wins.

**Environment**
- Local only: no AWS or other cloud accounts, paid services, externally hosted identity providers or AI APIs.
- Stack: Python, FastAPI, PyJWT with cryptography, stdlib `sqlite3`/`hashlib`/`pathlib`, pytest with httpx2 (AM-9), and setuptools as the build backend.
- uvicorn was added at M1M with the reviewer's approval of exact pins (`uvicorn==0.54.0`, the minimal install, and `click==8.5.0`; V11, AM-27).
- Not used: python-multipart, any ORM, Docker, or a frontend.

**Identity** (Addendum §5.1, §5.5; implemented in M1E-1 and M1E-2, with details in AM-14 to AM-16)
- ES256 tokens are verified locally: signature, pinned algorithm, `iss`, `aud`, `exp` and `nbf`.
- Tokens carry identity only. Role or `productions` claims are ignored.
- The public verification keys (one to eight, AM-14) come from a settings file path. The app refuses to start if the key set is missing, unreadable, empty, or contains private key material.
- No private key is ever committed. `src/` cannot mint tokens.
- Test issuers live in `tests/support/`. The dev issuer is in `tools/` and writes to the git-ignored `.dev/`.

**Authorisation** (Addendum §5.7)
- The engagement is looked up on every request; deny by default.
- Expiry is `now >= ends_at`, using an injected clock.
- End dates are mandatory and capped.
- Missing and forbidden objects get identical responses, and denials are logged.

**Content trust** (Addendum §5.1–§5.3)
- H is the SHA-256 of the stored bytes, computed by the server at seal.
- Binding chain: bytes → H → verdict → acceptance → promoted bytes.
- Caller-declared values are used only for consistency checks and display.
- Check order: size, declared checksum, file signature, then scanner. The outcome table in Addendum §5.2 is normative.
- The only shipped scanner is `lab-synthetic-marker` (kind `synthetic`). `create_app` has no default scanner, and the README states that the scanner gives no malware protection.
- The 30 s timeout is exercised through a scripted fake that raises `ScannerTimeout`. Tests never wait in real time.

**Promotion** (Addendum §5.4)
- Intent-first protocol (P1–P4) with an idempotent reconcile step.
- Never claim that a filesystem rename and a SQLite commit together are atomic.

**Isolation** (Addendum §5.5)
- `labs/` sits outside `src/` and outside package discovery.
- AST guards enforce the boundary.
- No environment variable, CLI argument or settings field can select a seam.
- Lab apps run in-process only.
- **M1C guards** (`tests/guards/test_isolation.py`) are AST checks. Over `src/` they flag: imports of `labs` or `tests`; environment-variable, `sys.argv` and command-line-parser use outside `ENVIRONMENT_READERS` (empty; a module is added by a reviewed edit in the slice that needs it); identifiers containing the word "vulnerable" or a listed synonym; `eval`, `exec`, `__import__`, code-loading modules such as `importlib`, and `sys.path`/`sys.modules` access; and any `FastAPI(...)` construction that leaves the documentation URLs enabled, whether written directly, as `module.FastAPI(...)` or through a `from fastapi import FastAPI as name` alias. Any mention of `dependency_overrides` is flagged in `src/` and `labs/`; in `tests/` only a read-only comparison is allowed (AM-10).
- **M1C evidence and limits:** every rule is run against bad and good samples in each test run, and on 2026-11-03 a bad file injected into a scratch copy of the tree, one per violation class, failed exactly the expected guard. The guards catch accidents and drift (R7); they do not prove isolation, and they cannot see a selector that is named differently or reached through syntax the rules do not list. A `FastAPI` subclass or a rebinding such as `API = FastAPI` is not followed.

**Working agreement**
- Follow the user-level `~/CLAUDE.md` and the slice rules in Addendum §6, as amended by AM-5 and AM-6.
- List the files before editing. About 3 files or 150 lines per step is a review guideline (AM-5).
- Use edit tools only.
- Write a failing test first, and never weaken a test.
- Report actual test output.
- No commits.

**Documentation** (Addendum §6)
- The README is the primary artefact.
- `docs/claims.md` maps every claim to a test ID.
- Banned wording: "secure", "safe", "protected", "production-ready", and performance or incident figures.
