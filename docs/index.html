Content Boundary Lab

A small web service where an outside vendor delivers a file to a film or TV production. Four bugs are planted in it, one function each. The lab runs the same attack twice: once against the buggy version and once against the corrected one, so you can read the flaw and the fix side by side.

  • v0.1 educational preview
  • Synthetic data only
  • Verified on macOS arm64, Python 3.13

View the repository · Read the Markdown version

How to read each finding

  1. Context: what the system is trying to do.
  2. The planted flaw: the one function that is wrong.
  3. The attack: the same steps against both versions.
  4. The fix and why: what the corrected code does, and the fixes that look right but are not.
  5. The result: the lab's real output.

The lab has no screen to capture. It is an API and a command-line program, so the panels on this page show its real output, copied from the evidence files in the repository (generated 2026-11-09 from commit 23b4560).

The setting

A studio runs two productions, ALPHA and BRAVO. A coordinator hires outside vendors for a limited time (an engagement, at most 90 days). A vendor uploads a file into a holding folder called quarantine. The server checks it, a coordinator accepts it, and only then does it move to the trusted store, where the production's people can read it. A vendor on ALPHA must never touch BRAVO.

  1. The vendor declares a deliveryname, size, SHA-256 hash. All of it is a claim.
  2. Who are you?A signed login token, valid for at most ten minutes.
  3. What may you touch?The engagement, looked up on each request, in the production the address names. F-06F-02
  4. Upload into quarantineA folder nobody trusts yet.
  5. Seal: should these bytes be trusted?The server hashes the stored bytes, then scans them. F-03
  6. The coordinator accepts exactly hash HOne specific byte string.
  7. Promotion to the trusted storeA system job copies the bytes, hashing as it copies. F-04
  8. Engaged people read the assetThe same checks run on every read.

Highlighted boxes are the three questions every request must answer. Each tag marks where a bug breaks one of them.

How the lab proves a bug is real. The corrected application is called the reference. For each finding, one function in it has a planted twin, the seeded variant. The lab swaps in only that one function and replays the same attacker steps. If the flaw is real, the attack works on the twin and fails on the reference.

F-02 · breaks “What may you touch?” · severity High in this scenario

Object access checks the parent, not the child

A vendor on ALPHA downloads BRAVO's unreleased file.

1 Context

A file is fetched with an address like /productions/ALPHA/assets/<id>. The server first asks whether you are engaged in ALPHA, the production named in the address. Two productions share one system, and a vendor on ALPHA must never see BRAVO's unreleased files.

2 The planted flaw
# labs/f02_parent_check/vulnerable.py def get_asset_in_scope(conn, caller, production_id, asset_id, now_micros): row = conn.execute(_LOOKUP, (asset_id, production_id, caller.issuer, caller.subject, now_micros)).fetchone() return None if row is None else Asset(*row)

The lookup uses the production from the address to check the caller, then loads the asset by its id alone. The asset's own production is never compared with the address. The check covers the door the request came through and never looks at the room the file is in.

3 The attack

The attacker is a vendor engaged only in ALPHA. They know the id of a BRAVO asset and ask for it through ALPHA's address.

Seeded variant (planted flaw)

  1. Request: ALPHA address, BRAVO file id
  2. Is the caller engaged in ALPHA? Yes
  3. Load the file by id no other check
  4. BRAVO's file is returned

Reference (fixed)

  1. Request: ALPHA address, BRAVO file id
  2. Is the caller engaged in ALPHA? Yes
  3. Does the file belong to ALPHA? No, it belongs to BRAVO
  4. 404, same as a missing file

4 The fix and why

The reference binds four things in a single database query: the asset, the production that asset really belongs to, the production named in the address, and the caller's current engagement. If any of them disagrees, the query returns nothing and the server answers 404, the same answer as for a file that does not exist.

Why it works. One query leaves no gap between checking and loading. Answering 404 in both cases means an attacker cannot tell whether BRAVO's file exists.

The fix that looks right and is not

Naive fix N1: check that the caller is engaged where the asset lives, and stop comparing with the address. It repairs every caller engaged in one production. It still fails vendors engaged in both: they can read BRAVO's file through ALPHA's address.

  • Naive fix N1Fails 2 rows, X4 and X5: the vendors engaged in both productions.
  • Alternative A1Holds all rows. A different complete fix: the asset must belong to the production the request named.

F-06 · breaks “What may you touch?” · High for a coordinator, Medium for a vendor

Authorisation snapshot in a long-lived token

A person keeps acting after their engagement was revoked.

1 Context

After login, the identity provider hands out a signed token that lasts at most ten minutes. The token proves who you are. What you may do lives in the engagement database, where a coordinator can revoke it at any moment and where it ends on a fixed date.

2 The planted flaw
# labs/f06_stale_authorisation/vulnerable.py (excerpt of authorize_engagement) claims = CARRIED.get() role = (claims.get("productions") or {}).get(production_id) if role is None: raise AuthorizationDenied(AuditReason.NO_ENGAGEMENT)

The seeded version reads your role from a productions claim that was written into the token when it was issued. A revocation or an end date that comes later is invisible to it, because the token still carries the old answer.

3 The attack

Two attackers. A vendor whose engagement a coordinator just revoked, and a coordinator whose own engagement was revoked while its token was still good.

Engaged
Revoked, token still valid: the seeded variant says yes
Token issuedEngagement revokedToken expires (at most 10 minutes)

Sketch, not to scale. For a coordinator the damage outlives the token: the grant it creates in that window can run for up to 90 days.

Seeded variant (planted flaw)

  1. The token carries the role written at login
  2. A coordinator revokes the engagement
  3. The same token is used again signature and time are still good
  4. Role read from the token: allowed

Reference (fixed)

  1. The token proves identity only
  2. A coordinator revokes the engagement
  3. The same token is used again engagement looked up now
  4. Engagement is revoked: 403

Row 8 is why a coordinator's case is worse. The 90-day grant is an ordinary database row. It outlives the stolen window, and it even survives fixing the code.

4 The fix and why

The reference looks the engagement up in the database on every request and believes one thing in the token: who you are. Role, production and end date come from the current row, and the end date is checked at the exact instant.

Why it works. A signature proves the token was issued. It cannot prove the permission still exists. Only the database knows about a revocation.

The fixes that look right and are not

Naive fix N1: check the token's validity again. A valid signature and an unexpired token do not show that the engagement is still active. Naive fix N2: read the store on each request and check revocation, but not the end date. It is right on the first request after a revocation and wrong from the end date on.

  • ReferenceHolds all 21 rows of the remediation matrix.
  • Seeded variantFails 8 rows: revocation, end date, role, a wrong production in the claim, the revoked coordinator's grant, and a token with no claim.
  • Naive fix N1Fails the same 8 rows.
  • Naive fix N2Fails 2 rows, X3 and X4: exactly at the end date, and one microsecond after it.

F-03 · breaks “Should these bytes be trusted?” · severity Medium here

Caller-declared checksum used as content identity

A flagged file passes the scan by borrowing a clean file's label.

1 Context

Scanning is slow, so the server remembers each verdict and reuses it for identical files. To know two files are identical it needs an identity, and the natural choice is the file's SHA-256 hash. The vendor declares that hash when it announces a delivery.

The lab's scanner is synthetic. It recognises one made-up marker string, which stands in for a malicious file. It protects against nothing real.

2 The planted flaw
# labs/f03_declared_identity/vulnerable.py def content_identity(delivery, stored): return ContentIdentity(delivery.declared_sha256)

The seeded version uses the hash the vendor declared as the file's identity. The server never measures the stored bytes. So the later check “does the declared hash match the file?” compares the claim with itself and cannot fail.

3 The attack

A vendor first delivers a clean file normally, so its verdict is cached. Then it delivers a marker file and declares the clean file's hash.

Seeded variant (planted flaw)

  1. Marker file, declared with the clean file's hash
  2. Identity = the declared hash never measured
  3. Cache lookup: “clean” hit
  4. SCAN_PASSED, scanner never asked

Reference (fixed)

  1. Marker file, declared with the clean file's hash
  2. Server hashes the stored bytes itself
  3. Measured hash differs from the declared one
  4. REJECTED (checksum_mismatch)

Row 4 shows 0 in both, for different reasons. The seeded version skips the scanner because it believes the cache. The reference stops at the mismatch before it gets to the scanner. Row 9 shows the scanner still works when the declaration is honest.

4 The fix and why

The reference hashes the stored bytes itself, in one pass, and uses that hash as the file's identity. It then compares it with the declared hash. A mismatch rejects the delivery before the cache is ever consulted.

Why it works. A trust decision has to rest on something the server measured. A label the sender wrote can say anything.

The fix that looks right and is not

Naive fix N1: also check that the cache entry belongs to the declared digest. The entry always belongs to the digest it was looked up by, so this check can never fail while that digest is still the vendor's claim.

  • ReferenceHolds all 11 rows of the remediation matrix.
  • Seeded variantFails 2 rows, X1 and X2: the original exploit, and the mismatch rejection that never happens.
  • Naive fix N1Fails the same 2 rows.

F-04 · breaks “Should these bytes be trusted?” · severity High if quarantine is writable after the seal

Promotion trusts a mutable reference, not the accepted bytes

The file that was approved is swapped before it reaches the trusted store.

1 Context

After sealing and scanning, a coordinator accepts one exact hash, H1. Later a system job promotes the delivery: it copies the file from quarantine into the trusted store. In between, the file is just sitting in a folder. The lab assumes something other than the application is able to write to that folder.

2 The planted flaw
# labs/f04_unverified_promotion/vulnerable.py def copy_verified(source, target, promoting): for block in source.chunks(): target.write(block) return target.finish()

Promotion copies whatever is in quarantine at that moment. It never compares what it wrote with H1, so the name copy_verified promises more than the code does.

3 The attack

After the coordinator accepted H1, something overwrites the quarantined file with different bytes of the same length. The lab assumes this step and does not show how it could happen.

Seeded variant (planted flaw)

  1. The coordinator accepts H1
  2. The file is swapped in quarantine same length, assumed
  3. Promotion copies what it finds no comparison with H1
  4. The trusted store holds the swapped bytes

Reference (fixed)

  1. The coordinator accepts H1
  2. The file is swapped in quarantine same length, assumed
  3. Promotion hashes the bytes while copying compares with H1
  4. INTEGRITY_FAILED, nothing published

Rows 6 and 8 are the worst part. The asset record and the audit trail both say the coordinator approved H1, while the bytes being served are different.

4 The fix and why

The reference counts and hashes the bytes as it writes them, and raises an error unless they are exactly the accepted bytes. Nothing is published unless what it wrote hashes to H1.

Why it works. Checking and using happen in the same pass, so there is no moment between the check and the copy for the file to change.

The fixes that look right and are not

Naive fix N1: compare the file's size with the accepted size. It stops swaps of a different length and lets a same-length swap through. Naive fix N2: hash the file in one pass, then copy it in a second pass. The bytes checked are not the bytes used, so a change between the two reads gets published.

  • ReferenceHolds all 11 rows of the remediation matrix.
  • Seeded variantFails 4 rows, X1 to X4: same-length, shorter, longer and emptied substitutions.
  • Naive fix N1Fails 1 row, X1: the same-length swap, which is the original exploit.
  • Naive fix N2Fails 1 row, X8: a change between the first and the second read.

One lesson from each

FindingThe mistakeThe rule
F-02Checked the door the request came through, then loaded the file by id alone.Check the thing you load against the thing you authorised.
F-06Believed a permission copied into a signed token.A signature proves who you are. Ask the database what you may do, every time.

The remediation matrices add a second lesson. For each finding the lab tries the original exploit, the behaviour that must keep working, the nearby variations, and the partial fixes that look like fixes. A fix is only good if it blocks every attack and breaks no legitimate use.

Run it yourself

You need a Mac with Apple silicon and Python 3.13. The install is checked by hash, and only that one platform has been verified. On Linux, Windows, an Intel Mac or Python 3.12 the install is expected to be refused. Without that machine you can still read the evidence files and write-ups linked above.

python3 -m venv .venv .venv/bin/python -m pip install --require-hashes --only-binary=:all: -r requirements.lock .venv/bin/python -m pip install --no-deps -e . .venv/bin/python -m labs

It ends with the summary line you saw above. Run one finding with python -m labs.f02_parent_check and all four remediation matrices with python -m labs.matrix.
