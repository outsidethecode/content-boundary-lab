F-06  Authorisation snapshot in a long-lived token
seam       content_boundary_lab.authz.authorize_engagement
twin       labs.f06_stale_authorisation.vulnerable.authorize_engagement
scenario   a vendor's signed token stays good after its engagement is revoked, or has ended

== REFERENCE
  1. a vendor with an active ALPHA engagement asks for its engagement and declares a delivery, with its signed token
       -> 200 vendor; 201 declared
  2. the ALPHA coordinator revokes that vendor's engagement
       -> 200 revoked
  3. the SAME token still verifies, as the same subject
       -> signature, issuer, audience and times are good for vendor-alpha-1
  4. the vendor asks for its engagement with that token
       -> 403 Forbidden
  5. what the audit trail recorded for that request
       -> access.denied denied (engagement_revoked), by vendor-alpha-1
  6. the vendor declares another delivery with that token
       -> 403; deliveries created after the revocation: 0
  7. it asks for an ALPHA asset (the asset lookup re-checks the engagement itself: the F-02 control)
       -> 403, never the bytes
  8. a vendor whose engagement ends in five minutes asks for it, then asks again 301 seconds later (past the end date, inside the token's life)
       -> 200, then 403
  9. a BRAVO-only vendor presents a token whose claim names ALPHA, and asks for its ALPHA engagement
       -> 403 Forbidden
